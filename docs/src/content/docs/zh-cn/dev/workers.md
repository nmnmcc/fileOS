## App 属于身份，而不是节点

文件在一个身份的各个节点之间同步，App 也必须同步。否则每台设备都有一份自己的 App，有自己的地址、自己的权限和自己的数据，用户得不到一致的体验。

- **每个身份有一个家目录**，同步到它的所有节点。一个人的文件夹（`/photos` 等）和 App（`/apps/…`）都挂载在这里。节点的根文件夹只保存这台机器自己的东西：引擎、缓存和设置。
- **App 安装进家目录。** 身份的每个节点都得到同一个 App。
- **一个 App 在一个身份内有唯一的名字**，在每台设备上的地址都相同：`http://photos.localhost:7341/`。
- 同一个名字被另一个 App 再次使用时，内核在它的第一个回应里发送 `Clear-Site-Data`，这样浏览器为旧 App 保存的数据不会交给新 App。
- 在没有节点的设备上，App 的地址是 `<app>.<身份>.<共享域名>`，请求会通过[会合](../identity/)找到这个身份当前在线的一个节点。
- **App 在每个节点上用同一把密钥行事。** 身份给自己的节点分发一个共享的 App 种子（节点加入时用 HPKE 发送），App 密钥由它派生。所以授权只需要做一次，而不是每个节点一次。

## App 是 Worker，而不是服务器

App 不会一直运行。它被一个事件唤醒，完成工作，然后停止。这是 Cloudflare Workers 和浏览器 Service Worker 的模型。

| 事件       | 什么时候                       | 接口                                 |
| ---------- | ------------------------------ | ------------------------------------ |
| `fetch`    | 有发给它的 origin 的 HTTP 请求 | `wasi:http/incoming-handler`（标准） |
| `change`   | 它监听的路径发生变化           | `fos:app/events`                     |
| `schedule` | 它请求的时间到了               | 待添加                               |
| `message`  | 另一个 App 或节点给它发消息    | 以后                                 |

- **每个事件一个新实例**，有 fuel、内存和时间的限制。没在工作的 App 不占内存。
- **清单里写明 App 接收哪些事件**：哪些路径、哪些时间。安装时，用户能看到它会在什么时候被唤醒、能碰什么。
- **App 的界面（`ui/`）由内核直接提供**，作为按哈希命名的文件，浏览器可以长期缓存。这些请求不会运行 App，所以大多数请求根本不运行 WebAssembly。
- **App 把数据保存在会同步的存储里**（可以合并的 `kv`，以及它的文件）。每个节点上的 `cache` 只用来加速，随时可能被删除。见[数据](../data/)。

## 事件在哪里处理

### 每个事件一个节点列表

每个事件有一个**按顺序排列的节点列表**，列出可以处理它的节点：

- 用户可以为每个 App 的每个事件设定列表，或者只让某些节点处理某个事件。这些设置保存在家目录里，所以每个节点读到的都一样。内核按设置执行（机制），用户的设置就是策略。
- 没有设置时，默认：
  - `fetch`：先由收到请求的节点处理，因为它最快，离线也能用；
  - `change` 和 `schedule`：先由常在线的节点处理（VPS、家里的盒子），然后是其他节点。
- 列表里的节点都不在线时，事件会等待，不会丢失。
- 请求到达一个不在列表里的节点时，内核通过 libp2p 把它转给列表中第一个在线的节点，再把回应送回来。例如，照片 App 的所有请求都可以交给家里的盒子处理，因为照片都在那里。

### 所有节点都在看，下一个接手

这是 SMTP 备用邮件服务器、Amazon SQS 可见性超时和 Temporal 心跳的做法：

1. **每个事件都有一个 ID**，每个节点都算得出来：日志记录的哈希加上处理函数，或者 App、任务和时间段。
2. **列表中的第一个节点处理事件**，其他节点等待。第 k 个节点在看到事件后等待 k × T；这段时间里没看到完成的标记，它就自己处理。
3. **长任务发送心跳**（“我在处理，T 秒内完成”），作为节点之间的消息，让其他节点继续等待。心跳不写进日志。
4. **结果和 “已完成” 标记作为一批一起写入。** App 的输出是 CRDT 数据，或者执行两次结果也相同的写入。所以即使两个节点都处理了同一个事件（一个太慢，或者网络断开），两份结果也会合并成同一个状态，浪费的只是计算。
5. **fileOS 之外的副作用**（以后会有：通知、外发请求）以事件 ID 作为幂等键，保证只发生一次。

没有专门的 “本地” 处理函数：事件产生的数据会同步，所以只需处理一次，每个节点都能得到结果。

## 和现在相比有什么变化

| 部分           | 现在                                      | 新的                                        |
| -------------- | ----------------------------------------- | ------------------------------------------- |
| App 放在哪里   | 节点的根文件夹；每台设备各装各的          | 身份的家目录；同步                          |
| 地址           | 按节点：`photos-<哈希>.localhost`         | 按身份：每台设备上都是 `photos.localhost`   |
| App 怎样运行   | 事件用一个常驻实例；HTTP 每个请求一个实例 | Worker：每个事件一个新实例                  |
| 事件在哪里处理 | 收到事件的节点                            | 用户设定的节点列表，带降级                  |
| App 的状态     | 只在一个节点上的 `kv`                     | 会同步、可合并的 `kv`；每个节点上的 `cache` |
| App 的密钥     | 由节点密钥派生                            | 由身份共享的 App 种子派生                   |

## 工作顺序

1. Worker：每个事件一个新实例，内核提供 `ui/`，清单列出事件。
2. 家目录：App 和 `kv` 移进去；`kv` 改为同步；增加 `cache`；共享的 App 种子。
3. 每个事件的节点列表，带降级和心跳。
4. `<app>.localhost` 地址，以及节点之间转发请求。
5. 登录（见 [HTTP 与浏览器](../http/)）。
