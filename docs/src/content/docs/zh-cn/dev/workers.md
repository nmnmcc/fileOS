## App 属于身份，而不是节点

文件在一个身份的各个节点之间同步，App 也必须同步。否则每台设备都有一份自己的 App，有自己的地址、自己的权限和自己的数据，用户得不到一致的体验。

- **每个身份有一个家空间**，同步到它的所有节点。它保存这个人的 App、设置和这个人的视图：哪些授权挂载在哪些名字下（`/photos` 等）。节点另外只保存这台机器自己的东西：缓存和设置。
- **App 安装进家空间。** 身份的每个节点都得到同一个 App。
- **一个 App 在一个身份内有唯一的名字**，在每台设备上的地址都相同：`http://photos.localhost:7341/`。
- 同一个名字被另一个 App 再次使用时，内核在它的第一个回应里发送 `Clear-Site-Data`，这样浏览器为旧 App 保存的数据不会交给新 App。
- 在没有节点的设备上，App 的地址是 `<app>.<身份>.<共享域名>`，请求会通过[会合](../identity/)找到这个身份当前在线的一个节点。
- **App 在每个节点上用同一把密钥行事。** 身份给自己的节点分发一个共享的 App 种子（节点加入时用 HPKE 发送），App 密钥由它派生。所以授权只需要做一次，而不是每个节点一次。

## App 是 Worker，而不是服务器

App 不会一直运行。它被一个事件唤醒，完成工作，然后停止。这是 Cloudflare Workers 和浏览器 Service Worker 的模型。

**有三种事件**：

| 事件       | 什么时候                         | 接口                                 |
| ---------- | -------------------------------- | ------------------------------------ |
| `fetch`    | 有发给它的 origin 的 HTTP 请求   | `wasi:http/incoming-handler`（标准） |
| `watch`    | 它监听的文件或前缀发生变化       | `fos:app/events`                     |
| `schedule` | manifest 中写明的时间，类似 cron | `fos:app/events`                     |

时间不是数据，所以它不是文件：`schedule` 写在 manifest 里，就像 Cloudflare 的 Cron Triggers。其他所有 “事件” 都是对文件的监听：

| App 在等什么     | 它监听什么                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------- |
| 数据的变化       | 这些文件或目录                                                                            |
| 授权的到来或离开 | 它视图里的 `/granted/`（见[模型](../access/)）                                            |
| 消息             | 它的收件前缀：一条消息就是发送者写在那里的一个文件，发送者需要对这个前缀有 `files.create` |

所以订阅只是对某个路径的 `files.watch`，用户像对待其他权限一样看到并授予它。

**App 订阅时，watch 带参数**，就像注册一个回调（和 CouchDB 的 `_changes`、Kubernetes 的 watch 一样）：

| 参数        | 作用                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| `recursive` | 是否包括路径下面的目录                                                                                   |
| `kinds`     | 要哪几种变化：新建、修改、删除                                                                           |
| `filter`    | 只要名字或类型匹配的，例如 `*.jpg` 或 `image/*`                                                          |
| `include`   | `none`（只要路径）、`meta`（大小、作者、版本）、`content`（内容，有上限）、`diff`（CRDT 文件的变化部分） |
| `batch`     | 攒多少个变化、或等多久，再调用一次                                                                       |
| `since`     | 从之前给出的位置继续                                                                                     |

每次调用收到一批变化和一个新的位置。调用成功结束，位置就向前推进；失败了，同一批变化会再送一次（至少一次）。

### 文件：`wasi:filesystem`

App 使用 WASI 0.2 标准的 `wasi:filesystem`，WASI 的预打开目录就是它的视图（见[模型](../access/#app-看到什么)）。

- 按位置读和流式读，就是 WASI 的调用（`read`、`read-via-stream`），建立在 HTTP 也在用的 `wasi:io` 之上。
- **写入会产生一个新版本**，和浏览器 File System Access API 的 `createWritable` 一样：App 可以在任意位置写入，没有改动的块和旧版本共享；文件关闭或同步时，新版本立即整体取代旧版本。在那之前，别人看到的仍然是旧版本。
- fileOS 只增加 WASI 没有的部分：watch、旧版本、冲突的多个版本，以及申请链接。

### 定时任务

App 在 manifest 中列出它的定时任务，就像 Cloudflare 的 Cron Triggers：

```toml
[[schedule]]
name  = "reindex"
every = "1d"        # s、m、h 或 d；最短一分钟
```

到了这些时间，内核向 App 自己的 `wasi:http` 处理函数发送 `POST /.well-known/fos/schedule/<name>`，并带上 `fos-event: schedule` 头。所以定时任务不需要在 App 接口里加任何东西。外部的请求永远到不了 `/.well-known/fos/` 下的路径，网关也会删掉它们的 `fos-event` 头。定时任务在节点启动一个周期后第一次运行；节点关闭期间错过的时间不会补上，和 cron 一样。目前每个节点运行它自己的 App 的定时任务。

### 用文件作为回应

和 nginx 的 `X-Accel-Redirect`（X-Sendfile）一样：要用一个文件回应请求时，App 告诉内核是哪个文件。内核以流的方式发送它，并处理 `Range`、`ETag` 和条件请求。App 不用把大文件读进内存，`Range` 也只在内核里实现一次，和提供 `ui/` 用的是同一段代码。

- **每个事件一个新实例**，有 fuel、内存和时间的限制。没在工作的 App 不占内存。
- **App 的界面（`ui/`）由内核直接提供**，作为按哈希命名的文件，浏览器可以长期缓存。这些请求不会运行 App，所以大多数请求根本不运行 WebAssembly。
- **App 的数据就是文件**（见[数据](../data/)）：
  - 需要保留的数据放在它的私有根目录下（实际是 `/appdata/<app>/`），会同步、合并、有版本；
  - 派生的数据（索引、缩略图）是每个节点上的缓存文件，内核可以随时删除；
  - 多人同时编辑的数据是内容为 CRDT 的文件，由内核合并。

## 事件在哪里处理

### 每个事件一个节点列表

每个事件有一个**按顺序排列的节点列表**，列出可以处理它的节点：

- 用户可以为每个 App 的每个事件设定列表，或者只让某些节点处理某个事件。这些设置保存在家空间里，所以每个节点读到的都一样。内核按设置执行（机制），用户的设置就是策略。
- 没有设置时，默认：
  - `fetch`：先由收到请求的节点处理，因为它最快，离线也能用；
  - `change` 和 `schedule`：先由常在线的节点处理（VPS、家里的盒子），然后是其他节点。
- 列表里的节点都不在线时，事件会等待，不会丢失。
- 请求到达一个不在列表里的节点时，内核通过 libp2p 把它转给列表中第一个在线的节点，再把回应送回来。例如，照片 App 的所有请求都可以交给家里的盒子处理，因为照片都在那里。

### 所有节点都在看，下一个接手

这是 SMTP 备用邮件服务器、Amazon SQS 可见性超时和 Temporal 心跳的做法：

1. **每个事件都有一个 ID**，每个节点都算得出来：日志记录的哈希加上处理函数，或者 App、任务和时间段。
2. **列表中的第一个节点处理事件**，其他节点等待。第 k 个节点在看到事件后等待 k × T；这段时间里没看到完成的标记，它就自己处理。
3. **长任务发送心跳**（“我在处理，T 秒内完成”），作为节点之间的消息，让其他节点继续等待。心跳不写进日志。
4. **结果和 “已完成” 标记作为一批一起写入。** App 的输出是 CRDT 数据，或者执行两次结果也相同的写入。所以即使两个节点都处理了同一个事件（一个太慢，或者网络断开），两份结果也会合并成同一个状态，浪费的只是计算。
5. **fileOS 之外的副作用**（以后会有：通知、外发请求）以事件 ID 作为幂等键，保证只发生一次。

没有专门的 “本地” 处理函数：事件产生的数据会同步，所以只需处理一次，每个节点都能得到结果。

## 和现在相比有什么变化

| 部分           | 现在                                      | 新的                                               |
| -------------- | ----------------------------------------- | -------------------------------------------------- |
| App 放在哪里   | 节点家空间中的一个空间；每台设备各装各的  | 身份的家空间；同步                                 |
| 地址           | 按节点：`photos-<哈希>.localhost`         | 按身份：每台设备上都是 `photos.localhost`          |
| App 怎样运行   | 事件用一个常驻实例；HTTP 每个请求一个实例 | Worker：每个事件一个新实例                         |
| 事件在哪里处理 | 收到事件的节点                            | 用户设定的节点列表，带降级                         |
| App 的状态     | 只在一个节点上的 `kv`                     | 文件：家空间里同步的文件，加上每个节点上的缓存文件 |
| App 的密钥     | 由节点密钥派生                            | 由身份共享的 App 种子派生                          |

## 工作顺序

1. Worker：每个事件一个新实例，内核提供 `ui/`，清单列出事件。
2. 家空间：App 和它的数据（文件，取代 `kv`）移进去；增加缓存文件；共享的 App 种子。
3. 每个事件的节点列表，带降级和心跳。
4. `<app>.localhost` 地址，以及节点之间转发请求。
5. 登录（见 [HTTP 与浏览器](../http/)）。
