本页记录 homeserver 的总体架构和技术路线。每个决定都写明理由，重要的决定还写明在什么情况下需要重新考虑。细节会在开发中调整，方向的改变则需要先讨论。

除非另有说明，本页的测量都在 2026-11-25 完成，使用 Rust 1.100 和一台 15 核的 Apple Silicon 电脑。"crate 数"统计的是正常（非开发）依赖图。crate 数只是背景信息，不是结论：一个拆分成许多小 crate 的库可以并行编译、增量重编更少，代价可能比一个大 crate 还小。我们评判一个依赖，看的是完整构建和增量构建的时间、二进制体积，以及它带进来了什么：第二套加密库或 HTTP 栈、`async-trait` 这类被禁用的 crate、重量级过程宏、构建脚本，或者 C 和 C++ 代码。

## 架构从哪里来

愿景里的几句话决定了架构的大部分：

- 1 核 CPU、1GB 内存服务 10 人的家庭，空闲内存低于 150MB。
- 一个程序加一个数据目录，复制目录就是备份。
- 二十年后数据还能完整读出来。
- 随时知道谁能看到什么，并且可以收回。
- 不懂技术的家人出了问题，能自己恢复。
- 一个人的服务器是一等公民，成本随你自己的生活增长，而不是随整个网络增长。

Web 的思想回答了这些要求：资源有 URL，可以有多种表示；不可变的东西谁都可以缓存，中间节点不需要被信任；客户端是用户代理，离线靠缓存；链接即关系；以及最小能力原则。

## 贯穿一切的规则

1. **建立在 Web 之上。** 一切都有 URL，一切都使用 HTTP，每个接口只要有开放标准就用开放标准，不只在边缘，homeserver 之间也是如此。
2. **一个可执行文件，一个数据目录。** `hs` 是一个文件，所有东西都链接在里面。运行时不下载任何东西，存储或其他任何功能都不需要别的程序。这条与其他规则冲突时，以这条为准。
3. **日志是事实，其他都是派生的。** 一个人保存的一切，都记录在签名的、只追加的日志和按内容寻址的 blob 里。表、搜索索引和预览图都由它们生成，随时可以丢掉重建。
4. **不可变的东西可以放在任何地方。** 封存的日志分段和 blob 永不改变，所以它们是可缓存的 HTTP 资源。本地目录、另一个 `hs` 或 S3 存储桶都能保存它们。同步、备份、迁移和联邦是同一个操作：取回缺少的部分。
5. **处处是同一套协议。** 每个节点使用同一套 HTTP API 和同一套格式。浏览器和手机是自己 homeserver 的用户代理：它们缓存数据、离线时把写入排队、保管设备密钥，但不各自运行一份服务器。
6. **你的节点就是你的信任边界。** 明文只存在于属于你的节点上。凡是离开、去往别人机器的东西（云存储桶、中继、信箱、不是成员的朋友的服务器），都先加密。
7. **一种权限模型。** 设备、应用、插件、AI 助手和朋友，都通过同一套 HTTP API 访问你的数据，凭的是授权（grant）。所有授权可以在一个地方列出，在一个地方收回。
8. **排序，而不是共识。** 每个共享的东西都有一台主服务器负责给它的事件排序。没有全局复制的状态，网络上也没有共识。
9. **不含 IO 的核心（sans-IO）。** 协议逻辑写成状态机，时间、随机数、存储和网络都从外部注入。同一份代码运行在生产环境和确定性模拟中。
10. **核心只提供机制，策略放在外面。** 为谁中继、哪些数据放在哪里、历史保留多久、接受陌生人的什么：这些都是带默认值的策略，可以由本人或插件替换。
11. **编译时间是预算。** 每个依赖都要测量，看的是构建时间、二进制体积和它带进来的东西，而不是它被拆成了多少个 crate。当一个库会带进一套平行的栈时，我们自己写小的实现。不用需要 cmake 的 C 或 C++；由 `cc` crate 编译的小型 C 代码（例如 SQLite）是允许的。

## 建立在 Web 之上

Web 是现存最大的去中心化系统：谁都能发布，谁都能链接，任何客户端都能读取。homeserver 采用它的思想和标准，而不是另起一套。

**一切都有 URL。** 每个对象、空间、日志、人和 blob 都是一个 HTTP 资源。路径以这个人的身份 ID 开头，而不是服务器名，所以换服务器后链接依然有效：身份日志说明当前由哪些节点为这个身份提供服务。域名只是别名。

**完整地使用 HTTP 语义。** 方法的含义就是 HTTP 规定的含义。blob 和封存的日志分段永不改变，所以它们的 ETag 就是哈希，并以 `Cache-Control: immutable` 和 `Range` 提供。更新使用条件请求（`If-Match`），过时的写入会得到 `412`，而不是悄悄覆盖。一个资源有多种表示，通过内容协商选择：联系人可以是 JSON、vCard 或网页；日程可以是 JSON 或 iCalendar；照片可以是原图或预览图。关系用链接表达（`Link` 头，RFC 8288），客户端顺着链接走，而不是自己拼 URL。

**客户端是用户代理。** Web 应用先渲染成 HTML，再用标准 Web Components 增强。离线使用的方式就是 Web 本来的方式：Service Worker 把不可变资源存进 Cache API，离线时的写入排队，联网后再发出，每个写入带一个幂等键，所以重试不会被执行两次。数据存放和查询的地方始终是服务器。

**homeserver 之间也用 HTTP。** homeserver 之间在我们的 QUIC 栈上使用 HTTP/3，退回时在 TCP 443 端口上用 TLS 承载 HTTP/2。空间的日志是一个可以按范围读取的资源；新事件 POST 到收件箱。请求用节点密钥按 HTTP 消息签名（RFC 9421）签名，所以请求经过中继时签名依然有效。我们自己定义的只有媒体类型和资源的含义。加入 `h3` 和 `h3-quinn` 增加 9 个 crate。

**登录、推送和应用都用 Web 标准。**

- 登录：通行密钥（WebAuthn）、OAuth 2.1 和 OpenID Connect，并用 DPoP（RFC 9449）把令牌绑定到设备。
- 通知：Web Push（RFC 8030、8291 和 8292），`hs` 是应用服务器。它适用于 Android、iOS 16.4 及以上和桌面上安装的 Web 应用。UnifiedPush 使用同一个协议。
- 插件：WebAssembly，一项 W3C 标准。插件接口建立在 `wasi:http` 之上，所以插件就是一个接收请求、返回响应的处理程序，很像 Service Worker。
- 插件界面运行在自己的源（origin）里，带严格的内容安全策略，由浏览器的同源模型隔离。
- 副本使用 S3 API 的一个子集，即带条件写入的普通 HTTP。

**格式。** HTTP API 使用 JSON。已有词汇表的地方就复用（ActivityStreams 2.0、schema.org、vCard、iCalendar），不重新命名。日志事件使用确定性 CBOR（RFC 8949 第 4.2 节），用 COSE（RFC 9052）签名，与 WebAuthn 用的是同一对。导出时，每种类型都写成它常见的开放格式。

## 数据模型

**资源。** 一个人保存的一切都是资源：照片、文件、消息、笔记、联系人、日程、密码。资源有类型、模式版本、字段，以及对 blob 的引用。

**实体与链接。** 人、地点、时间和事情也是资源。其他资源链接到它们。"打开一个人，看到和他有关的一切"是对链接的查询，不是每个应用各自实现的功能。原则 02 就落在这里。

**空间。** 空间是共享和同步的单位：你的私人空间、家庭、一个聊天、一本共享相册、一个共享文件夹。空间有成员（带角色的密钥）、一台主服务器和一条日志。

**日志。** 空间的日志是一串只追加的签名事件。事件是对某个资源的操作，用 HTTP 的话说就是创建、替换、修补或删除，带着新的表示或对它的引用。主服务器给每个事件分配序号，并用哈希把它们串成链。日志分段存放；写满的分段被封存，以哈希命名，此后永不改变。授权、成员变更和 MLS 提交也都是事件，所以它们和其他一切一样有序、可审计。

为什么用有序日志，而不是处处用 CRDT：权限变更无论如何都需要全序（Matrix 的状态解析展示了回避全序的代价）；有序日志对小服务器来说很便宜；MLS 的提交需要一个排序服务，主服务器本身就能提供。CRDT 只用在需要共同编辑的资源内部，比如协作文档，作为事件的载荷传递。离线时的编辑在客户端排队，到达主服务器时再排序。

如果主服务器永久消失，成员可以通过签名的交接，把空间迁到另一台主服务器，就像一个人迁移自己的身份一样。

**Blob。** 文件内容按 BLAKE3 哈希存放，相同的内容只存一份。传输时边流式接收边校验（Bao 的方式），所以不受信任的节点也可以提供 blob。

**遗忘。** 只追加的日志也必须支持真正的删除。哈希链覆盖的是每个事件载荷的哈希，而不是载荷本身，所以载荷之后可以被抹去，链依然能通过校验。删除事件会在每个跟随这条日志的节点上，抹去因此变得不可达的载荷和 blob。旧版本保留多久是本人的策略：永久、一年，或者完全不留。

**检查点。** 每次启动都重放多年的事件会很慢，所以主服务器会写签名的检查点：空间在某个序号时的当前状态，作为不可变对象放在分段旁边。节点从最新的检查点和其后的事件构建自己的表。

**二十年。** 日志和检查点的格式写在文档里，并保持很小，所以一个人只凭规范和一个 CBOR 库就能读出自己的数据，不需要 `hs`。导出把同样的数据转成 vCard、iCalendar、Markdown、JSON 和原始文件。

## 存储

### 数据目录

```
data/
  logs/       每个空间一个目录：封存的分段、尚未封存的末尾、检查点
  blobs/      按 BLAKE3 哈希存放的文件内容
  keys/       节点密钥和存储密钥（个人密钥不放在这里）
  index.db    SQLite：派生数据，可以放心删除
```

复制 `logs/`、`blobs/` 和 `keys/` 就是一份完整的备份。`index.db` 缺失、损坏或来自旧版本的 `hs` 时，会被重建。

### 副本

**存储只需要 `hs`。** 副本保存分段、检查点和 blob 的拷贝，它是以下之一：

- 本地目录，比如一块外接硬盘。`hs` 自己写文件：先写临时文件，`fsync`，再重命名。
- 另一个 `hs`：家里的设备、你租的 VPS，或朋友的 homeserver。它把分段和 blob 作为普通的 HTTP 资源提供，并接受用你的节点密钥签名的写入（RFC 9421）。租来的 VPS 或朋友的 homeserver 通常是盲节点，只保存密文。
- 兼容 S3 的存储桶，可选：云服务商，或者你本来就在运行的 Garage、MinIO。

封存的分段和 blob 永不改变，所以每种副本操作都一样：列出对方有什么，复制对方缺的部分。

- 同步和备份：让副本保持最新。
- 迁移：先同步，再把副本设为主存储，可选择删除旧的拷贝。
- 混合放置：日志处处都有，照片只放在副本上、本地留缓存，或者反过来。哪些数据放在哪里，是本人的策略。
- 联邦也是同一个机制：成员的 homeserver 跟随共享空间的日志，并取回它需要的 blob。

唯一可变的是每条日志的头：最后的序号和哈希，由主服务器签名。写入新的头使用条件写入（S3 上是 `If-Match`，另一个 `hs` 上是比较并交换），所以两个写入者不可能同时成功，也不需要锁服务。

`hs` 也提供它自己用到的那部分 S3 API（PUT、带 `Range` 的 GET、HEAD、DELETE、ListObjectsV2、条件写入、签名第 4 版），所以 `rclone` 等其他 S3 工具也能读写 `hs` 的副本。S3 客户端和这个服务端我们都在 hyper 和 `ring` 之上自己写（签名第 4 版只有几百行）。AWS SDK 远远超出我们的预算；`s3s` 服务端框架会在 tokio 加 hyper 的 28 个 crate 之上再多出 115 个，大部分来自它引入的 `async-trait` 和第二套加密库（RustCrypto 的 `hmac`、`sha2` 和 `md-5`）。

**在边界上加密。** `hs` 在每个分段、检查点和 blob 离开你的节点之前加密（`ring` 中的 AES-256-GCM，每个对象一个由存储密钥派生的密钥），并用带密钥的哈希给它命名，所以保存者既看不到内容，也看不出哪些文件相同。

### 派生状态：SQLite

每个保存明文的节点，都用 SQLx 和编译进来的 SQLite（SQLite 驱动的 `bundled` 特性）从日志构建自己的 `index.db`。SQLx 是异步的，与节点的 tokio 运行时直接配合；不启用宏，查询都是静态 SQL 字符串加绑定参数：

- **当前资源：** 每个资源的最新表示，读取只需一次查找。
- **链接：** 资源与实体之间的边表。"和这个人有关的一切"、"这个地方这些年"以及时间线，都是带索引的查询。
- **搜索：** 带 BM25 排序的 FTS5（见下文）。
- **地点：** R*Tree 模块，用于"在这附近发生过什么"。
- **本地 AI 的记忆：** 本人可以查看、修改和删除的事实与摘要，和其他东西一样作为资源保存。

索引从不复制，也从不离开节点。它的模式可以自由改变：需要不同模式的新版 `hs` 会从日志重建索引，而不是迁移它。使用 WAL 模式：写入走只有一个连接的写连接池，所以写入是串行的；读取走另一个有几个只读连接的连接池。扩展加载始终关闭。

**搜索。** FTS5 自带的分词器处理不好中文。我们在 SQLite 3.51 上测试过：用 `trigram` 分词器，`人民公园` 和 `妈妈去` 能找到，但 `公园` 这样的两字词找不到，因为 trigram 至少需要三个字符；`LIKE '%公园%'` 只能靠扫描整张表才找得到。可行的做法是：在建索引和查询时，把连续的中日韩字符切成相互重叠的两字片段，其他文字交给 `unicode61` 分词器。这样，`公园`、`妈妈`、`散步`、`人民公园` 和 `walk` 都找到了正确的行，并按 BM25 排序。我们把它注册为自己的 FTS5 分词器，所以原文只存一份。如果质量不够，以后可以加入 jieba 这样的分词。

**分析。** 个人数据很小：十万张照片和几百万条消息，SQLite 足以容纳。需要重度分析时，导出可以写成 Parquet 或 CSV，DuckDB 等工具可以作为接入的应用运行。

**测量过但没有选择的方案。**

- **DuckDB 加 DuckLake**，之前的选择。它提供快照、时间旅行和较强的分析能力，我们也做到了把 DuckDB 静态链接进一个 56 MB 的二进制。但中文搜索需要 tantivy 扩展和 jieba（133 个 crate，还没有确定的编译进来的方法），DuckLake 不能在浏览器里运行，把 `ducklake` 和 `fts` 构建进静态库需要修改 Nix 中的 DuckDB 构建，C++ 构建还需要给"不用 cmake"的规则开例外。日志成为事实之后，数据库只是索引，SQLite 就够了。
- **Turso**：稳定版 0.8 没有全文搜索（它的 tantivy 特性在 Rust 1.100 上编译不过）。0.9 预发布版只能用 `ngram` 分词器搜索中文，而且要打开实验开关。基础栈增加到 268 个 crate，4 个并行任务 50 秒，而 SQLite 是 13 秒。它的文件格式与 SQLite 兼容，索引又可以重建，所以以后切换的代价很低；Turso 到 1.0 时我们再评估。
- **tantivy 和 jieba-rs** 作为我们自己的搜索引擎：133 个 crate，在 Rust 1.100 上可以顺利编译。它会是 SQLite 旁边的第二个索引，有自己的文件需要保持一致；只要 FTS5 加两字片段搜得够好，就不需要它。它的构建时间还没有测量。

## 处处是同一套协议

服务器、手机和浏览器共享的是协议和格式，而不是整个服务器的拷贝：

| 位置         | 运行什么                                           | 离线时                             |
| ------------ | -------------------------------------------------- | ---------------------------------- |
| 服务器、桌面 | `hs`：日志、blob、索引、HTTP API                   | 它就是数据的家                     |
| 手机         | 原生外壳（UniFFI），保管设备密钥，负责上传，带缓存 | 已缓存的资源、排队的写入、照片上传 |
| 浏览器       | Web 应用；带 Cache API 和写入队列的 Service Worker | 已缓存的资源、排队的写入           |

**可移植 crate。** `hs-core`（格式、CBOR、COSE）、`hs-identity` 和 `hs-plugin-api` 标记为 `[package.metadata.hs] portable = true`，必须能为 `wasm32-unknown-unknown` 构建：插件是 WebAssembly，手机外壳通过 UniFFI 使用同样的 crate，Web 应用也可能用它们校验签名。`check` 会为这个目标编译它们。一个可移植栈（CBOR、BLAKE3、Ed25519 和 `ring`）的测试构建在 WebAssembly 中运行，BLAKE3 哈希与原生构建一致。

**角色是能力，不是程序的种类。** 节点会声明自己能做什么：是否一直在线、能否被公开访问、能存多少、能否保存明文、能否担任空间的主服务器。家里的设备可以承担所有角色。租来的 VPS 可以是只保存密文的盲节点。如果以后确实需要，手机也可以成为一个小节点，协议已经允许这样做。

**为什么不在浏览器里运行服务器。** 我们最先设计的就是这个方案。它意味着在 Worker 里运行 DuckDB-Wasm、使用 OPFS，再加上一条跑不了 DuckLake 的第二条存储路径，只为在本地回答查询。而人们离线时做的大部分事情（看最近看过的东西、记录内容），缓存就能应对，只需几 KB，也正是 Web 本来的工作方式。缓存做不到的事，比如离线搜索整个档案，我们有意不做。

## 身份

**个人密钥。** 一个人就是一对 Ed25519 密钥。身份 ID 由公钥派生，不需要任何注册机构。域名只是别名。

**身份日志。** 一条用个人密钥签名的、简短的只追加日志，声明当前的节点密钥、设备、地址、域名别名和密钥轮换。换服务器只需追加一条记录。任何持有这条日志的人都能校验它，不需要询问第三方。节点也把这条日志作为 W3C DID 文档提供，其他软件可以用标准工具解析它。我们向 KERI、`did:plc` 和 Keybase 的签名链学习，但不依赖其中任何一个。

**恢复。** 丢失个人密钥不应意味着失去一切。本人选择一种或几种恢复方式：打印的恢复包、口令，或者社交恢复，把密钥分给信任的朋友保管（Shamir 秘密共享，如 Dark Crystal）。用哪些方式是本人的策略。

**节点密钥。** 每个节点都有自己的 Ed25519 密钥，列在身份日志里。节点之间，它在 TLS 1.3 中作为原始公钥出示（RFC 7250，rustls 支持），每个节点也用它给 HTTP 请求签名。节点之间没有证书颁发机构。

**设备。** 新设备通过通行密钥（WebAuthn）加入，获得一个设备密钥和一项授权。设备不持有个人密钥。我们在 `ring` 之上自己写需要的那一小部分 WebAuthn：`webauthn-rs` 通过 RustCrypto 完成密码运算（RSA、P-256 到 P-521、argon2 等），这是 `ring` 之外的第二套加密库。

**地址发现。** 签名的地址记录（pkarr 的方式）发布到你联系人的 homeserver 上，它们本来就在为你中继；也可以选择发布到 DNS。不依赖任何公司的服务器。

**内置身份提供方。** homeserver 为上面的每个人提供 OpenID Connect（带 PKCE 的授权码流程，遵循 OAuth 2.1）。插件、接入的应用以及任何支持标准登录的服务，都使用同一个身份。对不支持 OIDC 的应用，homeserver 的反向代理自己检查会话（forward auth）。ID 令牌用 EdDSA 签名，为了兼容也支持 ES256，两者都在 `ring` 里。身份提供方只是几个端点，所以我们自己写。`openidconnect` 是客户端库，不是提供方，而且它也会带进 RustCrypto 的 RSA 和椭圆曲线。

## 权限

原则 05 要求随时知道谁能看到什么，并且可以收回。只有当这件事只有一个地方可看时，才做得到。

**所有人都是同一套 API 的客户端。** 你的设备、Web 应用、接入的应用、插件、通过 MCP 访问的 AI 助手，以及朋友的 homeserver，都通过同样的 HTTP 资源访问你的数据。没有谁能直接访问数据库。

**授权。** 一项授权说明：谁（一个设备密钥、一个 OAuth 客户端、一个插件、一个人），能访问什么（URL 前缀、资源类型、空间），怎样访问（读、写、分享），到什么时候。授权是你私人日志里的事件，所以它们有序、有签名，并保留在历史里。OAuth 的 scope、插件的能力和 MCP 的访问权限，都用授权来表达。共享空间以带角色的成员来扩展，方式相同。

**查看与收回。** "谁能看到这张照片？"和"这个应用能访问什么？"都是对授权和成员关系的查询。每项授权都有一份保存在你节点上的访问记录。收回只需一个事件。对端到端加密的空间，移除成员还会轮换 MLS 组密钥。别人已经复制走的东西无法收回，界面会明确说明这一点。

## 网络

**技术栈。** 只启用所需特性的 tokio，QUIC 用 quinn，rustls 配 `ring` 后端，HTTP/1.1 和 HTTP/2 用 hyper，HTTP/3 用 `h3`。这些是 iroh 也在用的基础组件，但不带 iroh 自己的那几层。不含数据库时，这个栈是 74 个 crate，`h3` 再增加 9 个。

**路径层。** `hs-net` 通过 quinn 的 socket 抽象，在 quinn 下面加一个以对端密钥寻址的虚拟 UDP socket。它为每个对端选择最好的路径：直连 IPv6，通过端口映射或打洞直连 IPv4，或者经过中继。路径变化时，QUIC 的连接迁移让连接保持不断。这就是 iroh 的 magicsock 背后的思路。iroh 的 QUIC 分支 noq 按照 IETF 草案，把 NAT 穿透和多路径做进了 QUIC 本身，上游 quinn 还不支持。等它们成为 RFC 并进入上游 quinn，我们就采用。在此之前，我们这一层保持小巧、可替换。

**NAT 穿透。** IPv6 优先。端口映射支持 PCP、NAT-PMP 和 UPnP-IGD，由我们自己写：`igd-next` 只支持 UPnP-IGD，还在 hyper 之外带进自己的 HTTP 客户端（`attohttpc`）和两个 XML 库。双方互相告知自己观察到的对方地址，就像 QUIC 地址发现草案那样。打洞通过一条已有的中继连接来协调。

**中继就是 homeserver。** 任何可达的 homeserver 都可以按主人的策略，为主人信任的人中继、收信、保存加密副本。中继的流量是端到端加密的，中继只能看到哪些密钥在相互通信。官方中继可以存在，作为又一个选择，也作为还没有朋友在用 homeserver 的人的第一个联系点。朋友发来的邀请链接会带上朋友的中继。没有官方中继，一切照常工作。对封锁 UDP 的网络，中继也接受 TCP 443 端口上的 TLS 连接。

**从浏览器访问你的 homeserver。** 浏览器需要普通的 HTTPS URL，你自己需要，打开共享相册链接的朋友也需要：

1. 有公网地址和域名时，由主人在 `hs` 前面放一个反向代理（Caddy、nginx）。`hs` 不实现 ACME：公网域名的 HTTPS 已有成熟方案，项目的精力放在点对点可达性上。
2. 没有公网地址时，一台可达的 homeserver（朋友的、你自己的 VPS 或官方的）按 SNI 转发 TLS，但不终止 TLS。TLS 仍然在家里结束，转发者只能看到密文。
3. 在局域网里，或者 Web 应用已经知道节点的密钥时，浏览器可以使用带 `serverCertificateHashes` 的 WebTransport，两者都不需要。WebTransport 自 2026 年 3 月起已是所有主流浏览器的 Baseline 功能。

## 加密

- **传输中：** 处处使用 TLS 1.3，节点之间使用节点密钥，上面再加签名的 HTTP 请求。
- **存放在你的节点之外时：** 放在不由你控制的副本上的每个分段、检查点和 blob，都由 `hs` 在上传前加密（见"副本"）。
- **共享空间：** 在成员的 homeserver 之间用 **MLS（RFC 9420）** 端到端加密。每个人的 homeserver 是一个 MLS 成员，而不是每台设备各是一个。这避开了端到端加密通讯软件需要处理的大部分多设备复杂性。空间的主服务器给 MLS 提交排序，和其他事件一样。中继、信箱和副本只保存密文。
- **盲节点：** 你租用的节点可以设置为只保存密文。它能中继、为加密事件排序、保存副本，但永远看不到明文。
- **库：** 只用 `ring`，因为 rustls 本来就需要它，而且它能为 WebAssembly 构建。混用多套加密库意味着要编译同一批 crate 的两代版本；我们的测试依赖图里出现了重复的 `digest`、`sha2`、`block-buffer` 等。我们使用 **mls-rs**（MIT OR Apache-2.0，由 AWS 维护；比基础栈多 63 个 crate，OpenMLS 是 95 个），配一个我们自己在 `ring` 之上写的小型加密提供者。

## 个人集群

一个人或一个家庭可以在一个身份下运行几个节点：家里的设备、VPS、笔记本。一个节点担任个人空间的主服务器，给它们的事件排序。其他节点跟随日志、构建自己的索引、提供读取；盲节点只保存加密副本。

主服务器的角色通过租约转移，需要多数有投票权的节点同意。只有两个有投票权的节点时，朋友的 homeserver 可以充当见证者，只负责打破平局，看不到任何数据。因为每个节点都已经有日志，转移角色不需要搬运数据。v1 只有一个服务器节点，加上放在另一个 `hs` 或存储桶上的加密副本。

## 插件

两类插件共用上面的权限模型：插件得到的正是本人给它的授权，本人可以查看和收回。

**WebAssembly 组件。** 它们运行在节点内部，由 wasmtime 沙箱隔离，接口用 WIT 定义，建立在 `wasi:http` 之上。插件处理路由给它的 HTTP 请求，和其他客户端一样通过 HTTP API 读写数据，只能向被授权的源发出请求。它还可以运行定时器、订阅事件、提供一个界面面板。任何能编译成 WebAssembly 组件的语言都可以使用。典型用途：导入工具、个人小工具、自动化、互助策略，以及通往 ActivityPub 等其他协议的桥接。

wasmtime 带 Cranelift 比基础栈多 64 个 crate，release 二进制增加约 7 MB。只用 Pulley 解释器时多 42 个 crate，构建时间约减半。wasmi 轻得多（16 个 crate），但不支持组件模型。wasmtime 依赖 `async-trait`，而 `deny.toml` 禁用了它，所以这条禁令只为 wasmtime 开例外。`hs-plugin-api` 中的插件端绑定只生成一次并提交到仓库，从不在 `build.rs` 中生成。

**接入的应用。** Jellyfin、Home Assistant、Forgejo 等专业软件作为独立程序运行，由本人或其操作系统安装。homeserver 不是容器平台。一个小型连接器（本身也是 WebAssembly 插件）描述这个应用，homeserver 随后提供：

- 登录：注册为 OIDC 客户端，或通过 forward auth；
- 随处可达：通过 homeserver 的 HTTPS 和 NAT 穿透，不需要开放端口；
- 通过授权有限地访问 homeserver 的数据，比如只读访问照片库；
- 事件和备份钩子。

## 客户端

- **一个 Web 应用。** 由 `hs` 提供，先渲染成 HTML，使用标准 Web Components 和一个小的打包文件，像文档一样由 Nix 构建，可以安装。
- **手机应用**只为 Web 应用在后台做不到的事而存在，比如上传新照片。它们是很薄的原生外壳（Kotlin、Swift），保管设备密钥，通过 UniFFI 使用可移植 crate，在 Web 视图里显示 Web 应用。
- **照片：** 手机在上传时用自己的硬件解码器生成预览图。服务器保存原图和这些预览图。服务器用纯 Rust 解码 JPEG、PNG 和 WebP。HEIC 和视频在宿主有 ffmpeg 时用 ffmpeg 处理，否则依赖客户端生成的预览图。
- **通知：** 凡是 Web 应用能接收的地方都用 Web Push。iOS 上的原生应用需要苹果的推送服务，通过一个登记过的网关，它只负责唤醒应用、不携带内容，任何人都可以运行。
- **标准协议：** WebDAV、CalDAV/CardDAV、Bitwarden API、OpenID Connect，以及面向 AI 助手的 MCP。以后可能支持 JMAP。
- **AI：** 核心不内置模型运行时。本地模型（比如 llama.cpp 服务器）作为接入的应用，通过常见的 OpenAI 风格 API 连接。homeserver 提供记忆、授权和 MCP 这一层。

## 运维

**进程。** 一个可执行文件，一个数据目录。一个 tokio 运行时，少量工作线程；每个空间的日志由一把异步锁串行追加；SQLite 只有一个写连接和几个读连接；另有一个阻塞线程池处理哈希、加密和媒体。

**更新。** `hs` 下载签名的发布版本（对可复现的 Nix 构建做 Ed25519 签名），保留上一个二进制，重启并运行健康检查。检查失败就回滚到上一个二进制。更新从不原地迁移日志：新版本能读旧的事件格式，索引直接重建，所以回滚不会丢失任何东西。在 systemd 下使用 systemd 的重启机制。带 A/B 更新的设备镜像以后再做。

**恢复。** 如果 `hs` 发现索引损坏或与日志不一致，就删掉并重建它，并在健康页面上说明。没有人需要修复数据库。

**分发。** 每个平台一个静态可执行文件（Linux x86_64 和 aarch64，musl），SQLite 和 Web 应用都在里面；一个 NixOS 模块；以及给已经在用容器的人的容器镜像。macOS 构建用于开发。

**健康状态。** 一个用平实语言写的健康页面，说明哪里出了问题、该怎么做。日志留在本地。没有遥测。

## 测试

- 在一个进程里，对许多节点、网络、副本和故障做确定性模拟，建立在不含 IO 的核心之上。quinn 的协议核心也是 sans-IO 的，所以 QUIC 也能在模拟中运行。做法借鉴 FoundationDB 和 TigerBeetle。
- 对日志排序、成员关系、授权和副本同步做属性测试。关键的性质是：逐个事件增量构建的索引，与从头重建的索引完全相同。
- 对每个解析器（CBOR、WebDAV XML、WebAuthn 数据和 S3 响应）做模糊测试。
- `check` 会为 `wasm32-unknown-unknown` 构建可移植 crate。
- 针对真实客户端和服务做兼容性测试：DAVx⁵、Thunderbird、Bitwarden 客户端、常见的 OIDC 依赖方，以及兼容 S3 的存储（几家大的云服务商、Garage 和 MinIO，以及用 `rclone` 和 AWS CLI 访问作为服务端的 `hs`）。
