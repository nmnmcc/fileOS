## 目标

一个人有**一个身份**。任何知道这个身份的人，都能找到这个人的**所有节点**：家里的盒子、一台小 VPS、一台笔记本。这不需要任何公司、服务器或全局网络。

## 身份和节点是不同的概念

- **身份**是一个人。它是一个 `did:fos` 方法的 [W3C DID](https://www.w3.org/TR/did-core/)，例如 `did:fos:4kq…`。
- **节点**是一台机器，它有自己的 ed25519 密钥 `N`，同时也是它的 libp2p PeerId。

一个身份可以有多个节点，节点可以变化，身份的密钥也可以变化，但 DID 不变。

## did:fos：没有目录服务器的 did:plc

我们不发明新的身份。`did:fos` 就是 AT Protocol 的 [`did:plc`](https://web.plc.directory/spec/v0.1/did-plc) 方法，数以百万计的 Bluesky 账号都在用它。我们保留它的规则：

- **DID 是一条签名日志中第一个操作的哈希。** 没有人能造出另一个哈希相同的第一个操作，所以 DID 能自证。
- **每个操作给出身份的完整状态：**
  - `rotationKeys`：1 到 5 把控制身份的密钥，第一把优先级最高。
  - `verificationMethods`：按名字列出的、用于其他工作的密钥。其中 `fos` 是身份在 fileOS 中的**签名密钥**。
  - `alsoKnownAs`：身份的其他名字，例如一个域名（见[名字](#名字用域名作为另一个名字)）。
  - `services`：到哪里找东西。`fos_identity` 指出身份空间。
- **第一个之后的每个操作，都由前一个状态中的某把轮换密钥签名**，并用哈希指向前一个操作。
- **密钥用 `did:key` 表示**，一个操作最多 7500 字节、最多 10 个 verification method。
- **轮换密钥和签名密钥是不同的密钥**，和 AT Protocol 一样。轮换密钥能改变一切，所以可以离线保存，比如抄在纸上。签名密钥负责日常工作，放在一个节点上。

在 fileOS 中，这条日志保存在身份空间里，像其他数据一样同步。每个节点都用日志自身里的密钥来检查它，所以不需要信任任何别人。一个人是一个**主体**，不是空间，也不是文件：DID 指的是这个人，他拥有的空间各有自己的 ID（见[模型](../access/)）。

我们改了三处，每处都有理由：

| `did:plc`                                                                           | `did:fos`                                                                                                            | 理由                                                                                               |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 轮换密钥用 secp256k1 或 P-256                                                       | 所有密钥都用 ed25519，哈希用 BLAKE3                                                                                  | 这是 fileOS 其他部分用的密钥和哈希                                                                 |
| DID 是哈希的前 120 位                                                               | DID 是完整的哈希（52 个 base32 字符）                                                                                | 名字是给人看的；DID 是给机器用的，不需要短                                                         |
| 由目录服务器（plc.directory）保存日志、决定分叉的顺序，并为 72 小时恢复窗口提供时间 | 日志保存在身份空间里，在身份的各个节点和认识它的人的节点上。分叉时，第一个操作由优先级更高的轮换密钥签名的那一支胜出 | 没有中心。高优先级的密钥总能收回低优先级密钥做的事。没有时间窗口，因为没有服务器，就没有可信的时钟 |

DID 日志是每个节点都能验证的事实，所以由内核验证。这些格式属于节点之间的契约。

### 身份空间

每个身份有一个空间，由签名密钥拥有，所以只有签名密钥能写入它。里面有：

| 路径          | 是什么                                          |
| ------------- | ----------------------------------------------- |
| `/did/<哈希>` | DID 日志的操作，每个以它的哈希命名              |
| `/nodes/<N>`  | 节点证书：签名密钥声明 `N` 是这个身份的一个节点 |

操作能自我验证。签名密钥可以删除一个操作，但造不出操作，因为只有轮换密钥能给操作签名。

**节点证书**写明 DID 和节点，由签名密钥签名。只要这把密钥仍是身份的 `fos` 密钥，证书就有效。要移除一个节点，签名密钥删除它的证书即可。

身份的各个节点都保存这个空间的副本，关注这个身份的人也可以保存。在节点上，身份空间挂载在 `/identity`。

签名密钥丢失或被盗时，由一把轮换密钥写一个操作，换上新的签名密钥。因为空间的所有者不会变，新的签名密钥会建一个新的身份空间，并由这个操作指向它。

### 创建身份和添加节点

1. `fos identity new` 在本节点上生成一把轮换密钥和一把签名密钥，创建身份空间和第一个操作，并打印 DID。
2. 在持有签名密钥的节点上运行 `fos identity add-node <节点密钥>`。它把这个节点的证书放进身份空间，允许这个节点读取和保存这个空间，并打印空间的 ID。
3. 在新节点上运行 `fos identity join <空间 ID>`。它把空间挂载在 `/identity`，并从第一个节点获取它。

`fos identity remove-node <节点密钥>` 删除这个节点的证书，并收回它对身份空间的授权。

### 身份链接

一个人用带线索的 DID URL 分享自己的身份：

```
did:fos:<id>?r=<multiaddr>&r=<multiaddr>
```

`r` 是**线索**：会合节点或这个身份的节点。线索可能过时，但链接仍然可用，因为下面的其他查找方式不依赖它们。

### 名字：用域名作为另一个名字

我们原样采用 AT Protocol 的 handle。有域名的人（比如 `alice.example`）可以把域名作为身份的名字：

- 域名指向 DID：在 `_fos.alice.example` 放一条 DNS TXT 记录，内容是 `did=did:fos:…`；或者放一个文件 `https://alice.example/.well-known/fos-did`。
- DID 指回域名：`alsoKnownAs` 里有 `fos://alice.example`。
- 只有两边互相指向时，名字才有效。

唯一的改动是记录和文件的名字（用 `_fos` 和 `fos-did`，而不是 `_atproto` 和 `atproto-did`），因为同一个域名可能同时是某个 Bluesky 账号的 handle，而那个账号的 DID 不同。

## 两种记录

查找节点其实是两个问题，它们的变化速度相差很大：

|          | 哪些节点是我的       | 每个节点现在在哪里       |
| -------- | -------------------- | ------------------------ |
| 变化频率 | 很少：添加一台新设备 | 经常：IP 变了、换了网络  |
| 签名者   | 身份的签名密钥       | 节点密钥 `N`             |
| 存放在   | 身份空间（会同步）   | 地址记录，不写进任何日志 |

**地址记录**的内容是：节点 `N`，这些地址，序号 `seq`，有效期到 `t`。它由 `N` 签名。序号大的记录取代序号小的。默认情况下，地址是中继地址（通过 Circuit Relay），而不是家里的 IP 地址。

两种记录都有签名，所以任何节点都可以转交，但没有节点能伪造。帮忙的节点最多只能什么都不说。

## 会合节点

**会合节点**为身份保存地址记录，并把它们交给查询的人。它像 Nostr 的 relay，但小得多。

### Nostr 的 relay 为什么会集中到少数服务器上

Nostr 的 relay 做的事情很多：长期保存所有内容，按任意过滤条件回答查询（因此需要数据库和索引），提供信息流和搜索，防垃圾，还承担信箱。内容存在 relay 上，读者必须去内容所在的地方。运营 relay 成本很高，大家都集中到大 relay 上。

另外，Nostr 的用户自己不运行任何东西。客户端很薄，所以一切都只能放在别人的服务器上。而在 fileOS 中，每个人本来就运行着节点。

### 会合节点只做这些事

以下是规则，新功能不能突破：

- **只保存指针。** 很小的地址记录，每个身份大约 1 KiB。不保存内容，不保留历史。
- **只按确切的键查找。** 没有查询语言。
- **数据不在它上面。** 数据在保存各个空间的节点上。一个会合节点消失，只是少了一种找人的方式，不会带走任何数据。
- **只用内存就能工作。** 不需要磁盘。重启之后，节点会在几分钟内重新发送记录。
- **它是 `fos` 的一部分。** 任何有公网地址的节点都可以当会合节点，不需要别的程序，也不需要配置。一个节点也可以只当会合节点。
- **有限额。** 每个键的记录数有上限，每条记录的大小有上限，节点写入的频率有上限，记录会过期。

会合和其他几项工作是分开的：保存数据（`store` 权限）、为离线节点保存信件、中继连接。一个节点可以只做其中的一部分。真正花钱的是中继（带宽），所以它有自己的限额。

会合节点帮谁是一项策略，有默认值，可以替换。默认情况下，有公网地址的节点为主人的身份当会合节点，也为主人信任的节点服务。

### 项目的会合服务

项目也运营一个会合节点，放在一台小服务器上，同时提供有限额的中继。一台小服务器就足以服务非常多的身份：一百万个身份大约占 1 GB 内存，验证这些记录的签名大约只用十分之一个 CPU 核。

它没有特权：

- 它运行普通的 `fos`，和其他会合节点的代码、协议完全相同。它的地址不写在内核里。
- 它是策略里的默认值。新身份的会合节点列表里默认有它。`fos identity` 会显示它，一条命令就能删掉。
- 主人自己的节点优先。身份有公网可达的节点时，这个节点排在列表和链接线索的最前面。
- 它宕机时，不会有人失联。认识你的人已经有你的身份空间，只有第一次找你的人才需要它。

## 无法追溯的键

会合节点不能知道一条记录属于哪个身份，也不能有人列出所有身份。所以记录不按 DID 保存。在每一天（一个 24 小时的**时间段** `p`），身份的节点计算：

```
name = BLAKE3 derive_key("fos rendezvous name v1", DID || p)
key  = BLAKE3 derive_key("fos rendezvous key v1",  DID || p)
```

- 记录保存在 `name` 之下。这个名字每天都换，无法追溯到 DID。
- 记录用 `key` 以 XChaCha20-Poly1305 加密。里面是节点证书（由签名密钥签名）和地址记录（由 `N` 签名）。
- 知道 DID 的人可以算出 `name` 和 `key`，找到记录；不知道 DID 的人做不到。

在会合节点上，每个节点 `N` 在一个名字下有自己的位置。只有 `N` 能修改自己的位置，因为记录由 `N` 签名。别人可以在某个名字下放一些没有用的记录，但只有知道 DID 的人才知道这个名字，限额让这种情况很有限，读者也会丢弃验证不通过的记录。

在一个时间段的最后两个小时，节点同时发送下一个时间段的记录。查找时，先查当前时间段，再查上一个，以防时钟不一致。

### 为什么不用 Tor 的密钥盲化

Tor 洋葱服务从身份密钥推导出盲化密钥，并用盲化密钥给记录签名。这需要在每个时间段都用到身份的私钥（或者用它事先签好的证书）。在 fileOS 中，身份的私钥只在一台设备上，而这台设备可能离线。按上面的设计，节点可以独立完成全部工作，也不需要新的密码学：只用 BLAKE3、ed25519 和 XChaCha20-Poly1305，它们都已经在依赖树里了。

### 这样做隐藏不了什么

- 会合节点能看到是哪个节点密钥发送了记录，以及它来自哪个 IP 地址。
- 它能看到哪个节点查询了哪个名字。它看不到身份，但能看到节点 `X` 查找了节点 `N` 发送的记录，所以它能看到节点之间的联系。
- 知道你的 DID 的人能看到你的地址。默认情况下，这些是中继地址，不是你家里的地址。

通过朋友的节点代为查询可以隐藏更多，这留到以后再做。

## 怎样找到节点

要找到一个身份的节点：

1. **线索。** 询问链接里的会合节点和节点。
2. **会合节点列表。** 如果有身份空间的副本，就询问里面列出的会合节点。
3. **认识的人。** 询问当前连接着的节点。保存着 `name` 下记录的节点（作为会合节点，或者来自之前的查找）会回答。

只要这个身份的任何一个节点回答了，就能找到全部节点：它有身份空间，里面有每一张节点证书；同一个身份的各个节点之间也会互相发送最新的地址记录。

如果只知道 DID，没有线索，没有身份空间的副本，也没有共同的会合节点或朋友，就找不到。实际上，人们总是通过链接、二维码或朋友拿到一个身份，所以总会有线索。

## 协议

一个 libp2p request-response 协议 `/fos/rendezvous/1`，消息用 CBOR 编码：

- `Publish(record)`：回答 `Ok` 或 `Refused(reason)`。
- `Find(name)`：回答 `name` 之下的记录。

相关逻辑（记录、验证、限额、会合节点保存什么、查找的步骤）都是 sans-IO 的，放在一个 portable 的 crate 里，所以可以在 `fos-sim` 中运行。

## 计划

1. **身份：** `did:fos`（DID 日志、轮换密钥、签名密钥），身份空间，节点证书，身份链接，添加节点（`fos identity`、`fos identity new`、`fos identity add-node`、`fos identity join`）。已实现。
2. **更多密钥和名字：** 添加和更换轮换密钥与签名密钥，抄在纸上的恢复密钥，以及域名（`_fos` 和 `/.well-known/fos-did`）。
3. **地址记录：** 节点为自己的地址签名，同一个身份的各个节点互相发送。
4. **会合：** 按时间段推导名字和加密密钥，带限额的会合存储，查找的顺序，以及把项目的会合节点作为默认值。在 `fos-sim` 中测试。
5. **项目的会合节点：** 部署到服务器上。
