## 一切皆文件，内核只有一套访问规则

- fileOS 的数据只有文件夹里的文件。没有单独的键值存储，也没有单独的流：App 的数据是文件；一串记录就是一个目录，每条记录一个小文件。
- **没有授权引擎。** 内核只有一种固定的检查访问的方式，每个节点都一样，所以所有节点都会得出同样的结论。
- **规则由 App 制定。** 用户把一批文件的管理权交给某个 App，这个 App 再按自己的方式授予和收回权限、检查写入。想要不同的规则，就换一个 App。

## 授权

**授权**是访问的唯一形式。它授予一个**主体**：一个 App、一个人（一个身份）或一台设备（一个节点）。对三者来说，它是同一种东西。和 [Cloudflare API 令牌](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/)一样：

- 一项授权是一组**策略**。
- 一条策略是**效果**（允许或拒绝）× 一组**权限** × 一组**资源**。
- **拒绝优先于允许。** “整个文件夹，但不包括 `private/`” 就是一条允许加一条拒绝。结果与顺序无关，所以每个节点都得到同样的结果。

### 权限

权限是最小的单位，没有由其他权限组成的权限。

| 类别 | 权限            | 允许做什么                                |
| ---- | --------------- | ----------------------------------------- |
| 文件 | `files.list`    | 看到名字                                  |
|      | `files.read`    | 读取内容                                  |
|      | `files.create`  | 新建文件                                  |
|      | `files.change`  | 修改已有的文件                            |
|      | `files.delete`  | 删除文件                                  |
|      | `files.history` | 读取旧版本                                |
|      | `files.watch`   | 收到变化事件                              |
| 访问 | `access.view`   | 查看谁有权限                              |
|      | `access.give`   | 把自己有的权限给别人，但不能更多          |
|      | `access.take`   | 收回自己给出的权限                        |
| 规则 | `rules.set`     | 为写入设置检查（见[写入检查](#写入检查)） |
| 分享 | `share.send`    | 通过分享面板把文件发给另一个 App          |
| 保存 | `data.keep`     | 保存和转发密文，没有密钥                  |

### 资源

- App 的私有数据；
- 用户选定的一个文件或文件夹。文件夹包括它下面的一切。

### 模板用于给别人授权

用户把权限授予另一个人或一台设备时，可以从一个**模板**开始：一组有名字的权限。

| 模板 | 权限                                                              |
| ---- | ----------------------------------------------------------------- |
| 只读 | `files.list`、`files.read`、`files.watch`                         |
| 读写 | 只读，加上 `files.create`、`files.change`、`files.delete`         |
| 管理 | 读写，加上 `files.history`、`access.*`、`rules.set`、`share.send` |
| 中继 | `data.keep`                                                       |

模板本身没有任何含义，“管理” 只是一组权限。授权里保存的是权限本身，而不是模板的名字，所以以后修改模板，不会改变已经给出的授权。

**App 不使用模板。** App 申请的是具体的权限，所以它得到的正好是它需要的，用户也能看到并逐项选择。

### 转授和收回

- 有 `access.give` 的主体，可以把自己拥有的权限转授出去，但只能更少：更少的权限，或者更少的资源。
- 一项授权被收回时，从它转授出去的授权也一起失效。
- 移除和某个操作同时发生时，这个操作无效（强移除，见[数据](../data/#移除和写入同时发生时)）。身份的主人根密钥永远不能被移除。

## App：清单是上限，授权发生在运行时

和 iOS、Android 一样：

- **清单列出 App 最多可能申请的东西**：具体的权限，以及资源的种类（一个文件或一个文件夹），还可以带一个类型提示，例如 `image/*`。清单本身不授予任何东西。
- **App 在需要时才申请。** 照片 App 显示照片时只申请 `files.list`、`files.read` 和 `files.watch`；用户想上传时，才申请 `files.create`。
- **用户在内核的选择器里决定**（一个 “powerbox”，和 [Sandstorm](https://sandstorm.io) 一样）。用户选择文件或文件夹，可以取消勾选任何一项权限，也可以拒绝；以后可以随时收回整项授权，或者其中的某几项权限。
- App 不能申请超出清单的东西。
- 授权保存在身份的家目录里，所以在一台设备上的授权，在所有设备上都生效。

App 是一个没有自己窗口的 Worker，所以申请的方式和登录一样，靠页面跳转：

1. App 的页面把用户转到 `fos.localhost/grant?…`；
2. 用户在内核的页面上选择和决定。这个页面在内核的 origin 上，App 伪造不了；
3. 内核把用户转回 App。

## App 看不到文件在哪里

和 Android 的分区存储以及 Flatpak 的 document portal 一样：

- App 看到的是**它自己的视图**，而不是用户的文件树：
  - `/` 是它的私有数据（实际是 `/appdata/<app>/`），不需要授权；
  - 每项授权都在 `/granted/<句柄>/` 下。
- **句柄**不透露文件在哪里。App 看不到它上面和旁边的东西。
- **同一个文件在每个 App 里的句柄都不同**，所以两个 App 无法发现它们拿到的是同一个文件。
- 句柄一直有效，直到授权被收回。
- App 从自己的视图得知自己的授权：它们都在 `/granted/` 下，有授权到来或离开时，App 会收到变化事件。

## App 之间的分享

和 Android 的 intent 一样：

1. 能接收东西的 App 在清单里声明：

   ```toml
   [[receives]]
   action = "send"
   types = ["image/*"]
   path = "/receive"
   ```

2. 有 `share.send` 的 App 带着文件，把用户转到内核的**分享面板**。内核列出能接收这种类型的 App，由用户选择一个。
3. 内核给接收方 App 一项授权（它有自己的句柄），并带着句柄把用户转到它的 `path`。对接收方来说，这只是一个普通的 `fetch` 事件。

分享就是一项普通的授权：

- 默认是只读（单个文件不需要 `files.list`，只有 `files.read` 和 `files.watch`），只针对一个文件，并且一直有效，直到被收回。
- 它遵守转授的规则：App 只能分享它拥有的东西，而且不能更多。分享者的授权被收回时，分享也一起失效。

## 写入检查

对某些文件有 `rules.set` 的 App，可以为写入这些文件设置一个**检查**，用来实现权限表达不了的规则：大小上限、格式、谁可以在聊天室里发言。

一次写入会同步到每一个保存这个文件夹的节点，每个节点都必须对它得出同样的结论。所以检查有以下限制，和 CouchDB 的 `validate_doc_update`、Holochain 的验证一样：

1. **它只回答是或否**，并给出理由。它不写任何东西，不发送任何东西，也没有网络。写入之后的工作交给变化事件。
2. **它总是给出同样的答案：** 它拿不到时钟和随机数；它依据这次写入的**因果历史**（这次写入所依赖的记录）来判断，而不是某个节点当前的状态。每个节点的因果历史都相同。
3. **它的代码是固定的。** 检查所用组件的哈希经过签名写在文件夹里；新版本也是文件夹里的一次操作。每次写入都用它在图中所在位置当时有效的版本来检查。
4. **有多个检查时，必须全部同意。** 这与顺序无关，所以没有链，没有 `next()`，任何检查都不能改变另一个检查看到的东西。
5. **不检查读取。** 有 `files.read` 和密钥的节点已经拥有数据，检查拦不住它。谁能读，只由密钥决定。

fuel 的上限远高于检查所需，因为不同版本的运行时计算 fuel 的方式可能略有不同。

每个保存文件夹的节点都会运行这些检查，所以共享文件夹意味着朋友的节点要在沙箱里运行你的 App 的代码。不运行检查的节点会接受别人拒绝的写入，它的副本就会走上自己的路。那是它自己的选择。

## 节点

节点自己的选择（为谁中继、为谁保存备份、提供多少空间），不是对共享文件的访问。它们是节点的**设置文件**，放在 `/node/` 下，带默认值。拿到这些文件授权的 App 可以管理它们，和其他文件一样。

## 命令行

命令行是主人的一个入口，和选择器一样。它能看到真实的路径，因为主人能看到一切。

```
fos app grant <app> <路径> <权限>              例如：fos app grant photos /photos files.read,files.create
fos app grants [<app>]                        列出授权，展开每一项权限
fos app revoke <app> <句柄> [<权限>]           收回整项授权，或只收回其中几项权限
fos folder grant <路径> <身份或节点> <模板或权限>
```

## 一套逻辑覆盖全部

| 什么                 | 怎样实现                                  |
| -------------------- | ----------------------------------------- |
| 用户为 App 选择文件  | 一项授权                                  |
| App 分享给另一个 App | 一项授权，遵守转授规则                    |
| 命令行授予权限       | 一项授权                                  |
| 把文件夹分享给朋友   | 给朋友的身份一项授权，从模板开始          |
| 辅助节点保存你的数据 | 一项 `data.keep` 授权                     |
| App 得知自己的授权   | `/granted/` 下的文件，以及变化事件        |
| App 接收分享         | 一个 `fetch` 事件                         |
| App 的规则           | `access.give`/`access.take`，以及写入检查 |
| 收回                 | 强移除，连同转授出去的部分                |
| 每台设备都一样       | 家目录同步                                |
