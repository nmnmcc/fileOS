## 什么东西应该合成一个

fileOS 只有一个模型，但只有当两样东西**规则相同、生命周期相同、出错的方式相同**时，才把它们合成一个概念。把两样东西强行塞进一个概念，这个概念就会充满特例。所以本页既说明什么是相同的，也说明什么要分开，以及为什么。

## 七个概念

| 概念     | 是什么                                                                                 |
| -------- | -------------------------------------------------------------------------------------- |
| **内容** | 永不改变的字节，切成按 BLAKE3 哈希命名的块                                             |
| **文件** | 有固定 ID、会改变、有版本的东西；它的内容是普通字节或一个 CRDT                         |
| **空间** | 同步、所有者、密钥、检查点和保留策略的单位；内部是一组扁平的名字，每个名字对应一个文件 |
| **主体** | 人、设备、组或 App：会行动、可以被授权的一方                                           |
| **授权** | 给一个主体的访问权：作用在空间某一部分上的权限策略；保存在空间里                       |
| **视图** | 一个主体看到的文件树：它拿到的授权，挂载在它自己选的名字下                             |
| **事件** | 唤醒 App 的东西：一个 HTTP 请求、它监听的文件发生变化，或者一个时间                    |

### 内容

内容是存储层。块按哈希命名，所以同样的字节只保存一次，每个块都能校验，同步时只传缺少的块，文件的任意一段都能读取并校验（BLAKE3 是树形哈希）。内容不是文件的身份：文件改变时身份保持不变，而它的字节变了。

### 文件

所有需要保留的东西都是文件：人们的文件、App 的数据、缓存文件，以及聊天或动态的每一条记录（一个目录，每条记录一个文件）。没有键值存储，也没有流类型。

- 文件有一个**固定的 ID**，在创建时生成。改名不会改变它。
- 文件有**版本**。两台设备同时修改它时，各个版本并排保留，谁的修改都不会悄悄丢失。
- 内容是 **CRDT** 的文件（基于 [Loro](https://github.com/loro-dev/loro)）由内核合并，而不是保留为多个版本。
- **缓存文件**和文件一样，只是只在一个节点上：它不同步，计入缓存预算，内核可以删除它。这只是位置的不同，所以和文件合成一个概念。

### 空间

空间是许多系统都有、也都需要的东西：Willow 的 namespace、Matrix 的 room、git 的仓库、S3 的 bucket、Syncthing 的文件夹。（原型里叫 “文件夹”；换一个名字，是为了不和目录混淆。）

- 空间是**同步、所有者、密钥、检查点和保留策略**的单位。它的 ID 是它第一条记录的哈希，所以能自证。
- 在内部，空间是**一组扁平的名字**。名字里可以有 `/`；“目录” 只是名字的前缀。每个文件在它的空间里只有一个名字。
- 空间的日志由每个写入者的签名日志组成，形成一个因果图（见[数据](../data/)）。

### 主体

主体是行动的一方，文件是被操作的一方。它们规则不同，所以要分开。在主体内部，所有主体共用一个模型：

| 主体 | 它的权威                                                       |
| ---- | -------------------------------------------------------------- |
| 人   | 自己的轮换密钥：一个能自证的 [`did:fos`](../identity/) DID     |
| 设备 | 它的节点密钥，加上它所属的人签发的证书                         |
| 组   | 它的所有者，可以是一个人或另一个组；这条链最终落在一个人身上   |
| App  | 它属于一个人，用一把由这个人的各个节点共享的种子派生的密钥行事 |

主体的状态（DID 日志、组的成员）像数据一样保存和同步，但它由主体自己的密钥签名，并由内核验证。

**所有权是递归的。** 每个空间有且只有一个所有者，可以是一个人，也可以是一个组。每个组有且只有一个所有者，并且有成员。这条链最终落在某个人的主人根密钥上（优先级最高、永远不能被移除的那把轮换密钥）。不允许形成环。“以组的名义” 做的操作，只要签名的密钥能沿链追溯到组的所有者，就是有效的，和 Keyhive 的嵌套组一样；组没有自己的私钥。

## 授权

**授权**是访问的唯一形式，对所有种类的主体都一样。它**保存在它所涉及的空间里**，所以所有者随时都能看到谁有访问权。

- 一项授权是一组**策略**。一条策略是一个效果（允许或拒绝）× 一组**权限** × 一组**资源**。**拒绝优先。** 这是 [Cloudflare API 令牌](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/)的形状。
- 资源是空间里名字的一个**前缀**，或者**一个文件**（按它的 ID，所以改名不影响授权）。
- 授权写明**它从哪里来**：它是从哪项授权转授来的，或者来自所有者。

### 权限

| 类别 | 权限               | 允许做什么                         |
| ---- | ------------------ | ---------------------------------- |
| 文件 | `files.list`       | 看到名字                           |
|      | `files.read`       | 读取内容，并拿到它的密钥           |
|      | `files.create`     | 新建文件                           |
|      | `files.change`     | 修改已有的文件                     |
|      | `files.delete`     | 删除文件                           |
|      | `files.history`    | 读取旧版本                         |
|      | `files.watch`      | 监听变化                           |
| 访问 | `access.view`      | 查看这个资源上的授权               |
|      | `access.give`      | 转授自己拥有的，不能更多           |
|      | `access.take`      | 收回从自己这里转授出去的授权       |
| 规则 | `rules.set`        | 为写入设置检查；设定事件的节点列表 |
| 分享 | `share.send`       | 通过分享面板把文件发给另一个 App   |
| 保存 | `data.keep`        | 保存和转发密文，没有密钥           |
| 空间 | `space.checkpoint` | 代表所有者签发检查点               |

### 模板用于给别人授权

| 模板 | 权限                                                                                  |
| ---- | ------------------------------------------------------------------------------------- |
| 只读 | `files.list`、`files.read`、`files.watch`                                             |
| 读写 | 只读，加上 `files.create`、`files.change`、`files.delete`                             |
| 管理 | 读写，加上 `files.history`、`access.*`、`rules.set`、`share.send`、`space.checkpoint` |
| 中继 | `data.keep`                                                                           |

模板只是一组有名字的权限；授权里保存的是权限，不是模板的名字。**App 从不使用模板**：它们申请的是具体的权限。

### 规则

1. **转授：** 有 `access.give` 的主体，给别人的只能相同或更少：更少的权限，或更小的资源。
2. **收回：** 一项授权被收回时，从它转授出去的授权一起失效。
3. **强移除：** 与允许它的那项授权被收回同时发生的操作无效。它留在图里，但不产生效果，依赖于它的一切也不产生效果。
4. **检查一次写入：** 主体 P 的一次写入有效，当且仅当在它的因果历史中，存在一条从空间的所有者到 P 的有效授权链，并且这条链允许这次写入。只用到授权和因果顺序，从不使用时间，所以每个节点都得到同样的结果。
5. **冲突：** 两个操作不能同时成立时，链末端的所有者胜出。

### 写入检查

有 `rules.set` 的主体（通常是 App）可以为写入设置**检查**，用来实现权限表达不了的规则。每个节点必须得出同样的结论，所以和 CouchDB 的 `validate_doc_update`、Holochain 的验证一样：检查只回答是或否；它拿不到时钟、随机数和网络；它依据写入的因果历史判断；它的代码由签名写进空间的哈希固定；有多个检查时必须全部同意；不检查读取，因为谁能读只由密钥决定。

## 视图

**视图**是一个主体看到的文件树。它由**挂载**组成：主体持有的一项授权，放在**主体自己选的**一个名字下。

授权和挂载是有意分开的。授权是权威，每个节点都必须检查它，所有者也必须能把它们列出来。挂载只是持有者把它放在哪里。所以授权的一方从不写入持有者的视图：授权的一方签发授权，持有者（如果是 App，就由内核代劳）把它挂载起来，就像接受一个邀请。

| 谁的视图 | 里面有什么                                                                            |
| -------- | ------------------------------------------------------------------------------------- |
| 人       | 自己的空间，以及别人给他的东西，放在他自己选的名字下（`/photos/`、`/来自小明/2026/`） |
| 人       | 通讯录：他认识的人和组                                                                |
| App      | `/`：它的私有数据；`/granted/<句柄>/`：交给它的东西                                   |

**一个文件可以出现在许多路径上**，出现在许多视图里，而它在自己的空间里只有一个名字。同一个文件，对小明是 `/photos/2026/cat.jpg`，对妈妈是 `/来自小明/2026/cat.jpg`，对一个 App 是 `/granted/7Hq2/cat.jpg`。

### App 看到什么

- App 使用标准的 **`wasi:filesystem`**（WASI 0.2）；它的视图以 **WASI 预打开目录**的形式交给它。它可以使用自己语言的标准库（例如编译到 `wasm32-wasip2` 的 Rust 的 `std::fs`）。
- **句柄**是内核选的随机名字，不透露空间，也不透露文件的名字。同一个文件在每个 App 里的句柄都不同，所以 App 之间无法发现它们拿到的是同一个文件。
- 默认情况下，App 的数据不在用户的视图里（和 Windows UWP 一样）。所有者可以在看过警告后，给自己一项授权。

### 在运行时申请

- **清单是 App 最多能申请的东西：** 具体的权限、资源的种类（一个文件或一个前缀），以及可选的类型提示，例如 `image/*`。清单本身不授予任何东西。
- **App 在需要时才申请**，它把用户转到内核的选择器（一个 “powerbox”，和 [Sandstorm](https://sandstorm.io) 一样）。用户选择，可以取消勾选任何一项权限，也可以拒绝。内核签发授权，把它挂载到 App 的视图里，再把用户转回来。
- 没有 “照片库” 这样的系统级种类。
- 用户可以随时收回整项授权，或者其中的某几项权限。

### App 之间的分享

和 Android 的 intent 一样：App 在清单里声明它能接收什么（`[[receives]]`，写明 action、类型和路径）。有 `share.send` 的 App 把用户转到内核的分享面板；用户选择一个 App；内核用分享方自己的授权，给接收方一项授权（只读、单个文件、一直有效直到被收回），把它挂载好，再把用户转到接收方的路径，对接收方来说这是一个普通的 `fetch`。

### 命令行

命令行和选择器一样，是所有者的一个入口，能看到真实的名字：

```
fos app grant <app> <路径> <权限>              例如：fos app grant photos /photos/2026 files.read,files.create
fos app grants [<app>]                        一个 App 的授权，展开每一项权限
fos app revoke <app> <句柄> [<权限>]           收回整项授权，或只收回其中几项权限
fos space grant <路径> <主体> <模板或权限>
```

## 事件

| 事件       | 是什么                                                            |
| ---------- | ----------------------------------------------------------------- |
| `fetch`    | 发给 App 的 origin 的 HTTP 请求（`wasi:http`）                    |
| `watch`    | 它监听的文件发生变化，带参数（见 [App 作为 Worker](../workers/)） |
| `schedule` | 清单里申请的一个时间，和 Cloudflare 的 Cron Triggers 一样         |

App 的授权发生变化，以及消息（别人写进一个他有 `files.create` 的目录里的文件），都是数据，所以都是 `watch`。时间不是数据，所以不把它做成文件。临时状态（光标、“正在输入”）根本不保存，它以后会用一个单独的短消息通道。

## 一个例子

小明拥有一个空间 `S1`，里面的名字是 `2026/beach.jpg`、`2026/cat.jpg` 和 `private/diary.md`。

1. **小明的视图**把 `S1` 挂载在 `/photos/`。
2. **小明把 2026 年的照片分享给妈妈。** `S1` 里增加一项授权：给妈妈，只读，作用在前缀 `2026/` 上，来自所有者。妈妈把它挂载在 `/来自小明/2026/`。她看到的 `/来自小明/2026/cat.jpg`，和小明的 `/photos/2026/cat.jpg` 是同一个文件；她到不了 `private/`。
3. **照片 App 申请照片。** 小明选择 `/photos/2026/`，并额外勾选 `files.create`。`S1` 里增加一项授权：给这个 App，`files.list`、`files.read`、`files.watch` 和 `files.create`，作用在 `2026/` 上。内核把它挂载到 App 视图里的 `/granted/7Hq2/`。App 不知道 `S1`，也不知道 `2026/` 上面的名字。它上传 `dog.jpg` 时，`S1` 里出现名字 `2026/dog.jpg`，小明和妈妈都能看到。
4. **照片 App 把 `cat.jpg` 分享给聊天 App。** `S1` 里增加一项授权：给聊天 App，`files.read` 和 `files.watch`，作用在文件 `cat.jpg` 上（按它的 ID），来自照片 App 的授权。它被挂载在 `/granted/K9pa/cat.jpg`。
5. **小明把 `cat.jpg` 改名为 `best/cat.jpg`。** 聊天 App 的授权作用在文件的 ID 上，所以仍然有效。妈妈的授权作用在前缀 `2026/` 上，所以她不再看得到它。两者都符合当初给出的东西：一个文件，或者一个位置。
6. **谁有访问权？** 小明打开 `S1` 的访问页面，就能看到所有授权，因为它们都保存在 `S1` 里。
7. **小明收回照片 App 的授权。** 聊天 App 的授权来自它，一起失效。妈妈的授权来自所有者，保持不变。照片 App 在同一时间、在另一台设备上做的上传无效。
8. **组。** 家庭组的所有者是妈妈，小明和爸爸是成员。家庭相册 `S2` 的所有者是这个组。小明和爸爸各有一项来自这个组、作用在 `S2` 上的读写授权。冲突时，链末端的所有者，也就是妈妈，胜出。

## 什么是相同的，什么要分开

| 合成一个                                  | 原因                             |
| ----------------------------------------- | -------------------------------- |
| 所有保存的数据都是文件（没有 kv，没有流） | 规则相同：同步、版本、访问、保留 |
| 同步的文件和缓存文件                      | 只是位置不同                     |
| 人、设备、组和 App 的访问                 | 同一种授权，同样的检查           |
| 人的文件树、App 的句柄、通讯录            | 都是视图里的挂载                 |
| 数据的变化、授权的变化、消息              | 都是文件的变化：`watch`          |

| 分开                 | 原因                                                   |
| -------------------- | ------------------------------------------------------ |
| 文件和内容           | 文件改变时身份延续，字节则不                           |
| 授权和挂载           | 一个是每个节点都要检查的权威，一个是持有者自己选的名字 |
| 主体和文件           | 一个行动，一个被操作；由不同的规则签名和检查           |
| 空间和目录           | 一个是同步、所有者和密钥的单位，一个是名字的前缀       |
| 数据、时间、临时状态 | 只有数据需要保存                                       |
