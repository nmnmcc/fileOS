## 核心：路径就是能力

- **一切皆文件。** 数据、App 的数据、人、设备、组、通讯录、设置、消息、时间和临时状态，全都是文件和文件夹。
- **每个主体有自己的命名空间**：它看到的那棵文件树。命名空间本身也是一个文件夹。
- **命名空间里的每一个路径都是一个链接**：它指向一个对象，并带有权限。**你能通过哪些路径到达一个文件，以及这些路径上的权限，就是你对它的访问权。** 除此之外，没有任何其他的访问记录。
- **一个文件可以有多条路径。** 同一个文件，对一个人是 `/photos/cat.jpg`（读写），对另一个人是 `/来自小明/cat.jpg`（只读），对一个 App 是 `/granted/7Hq2/cat.jpg`。通过任何一条路径修改，改的都是同一个文件；每条路径能做的事不同。
- **没有授权引擎。** 内核只有一种固定的检查访问的方式，每个节点都一样，所以所有节点都得出同样的结论。规则由管理文件的 App 制定。

这结合了几个经过检验的设计：Plan 9 每个进程独立的命名空间，Capsicum 的能力（权限跟着你手里握着的引用，而不是跟着文件），以及 Tahoe-LAFS 的读能力和写能力。

## 所有文件的根：`/{身份}/{哈希}`

- **文件夹**是同步、日志和存储的单位。它的哈希（也就是它的 ID）是它第一条记录的哈希；内部是扁平的键空间（见[数据](../data/)）。
- **每个文件都有一个根路径，而且只有这一种形式：**

  ```
  /{身份}/{哈希}/{键}
  ```

  `{身份}` 是创建这个文件夹时所用身份的 DID，`{哈希}` 是文件夹的哈希，`{键}` 是文件夹里的键。例如 `/did:fos:ming…/F1/2026/cat.jpg`。目录也一样，只是换成前缀：`/did:fos:ming…/F1/2026/`。

- **对象就是这个路径。** 命名空间里的路径变化时，它不变。**其他所有路径都是指向它的链接。**
- 路径里的身份也说明了到哪里去找数据：这个身份的节点，通过[会合](../identity/)找到。

## 主体就是文件夹

**主体**是任何能持有链接的东西。每个主体都是一个文件夹，它的命名空间就在里面。

| 主体 | 权威从哪里来                                                              |
| ---- | ------------------------------------------------------------------------- |
| 人   | 自己的轮换密钥（[`did:fos`](../identity/)）；它的 DID 就是它的文件夹的 ID |
| 设备 | 它的节点密钥；它属于谁的设备，由那个人文件夹里的证书证明                  |
| 组   | 它的所有者（另一个主体），沿链往下                                        |
| App  | 它属于一个人；它用一把由这个人的各个节点共享的种子派生的密钥行事          |

- **一个人的 DID 就是他的文件夹的 ID：** `did:fos:<文件夹 ID 的 base32>`。这个文件夹的日志就是 DID 日志，不再有第二个 ID。
- **一个人展示给别人的东西**（DID 日志、节点证书、会合节点、其他名字）是他文件夹里的一个目录，认识的人只拿到这个目录的读链接。
- **通讯录**是你命名空间里指向你认识的人和组的文件夹的链接，例如 `/people/mom/`。

## 链接

一个链接包含：

| 字段   | 是什么                                         |
| ------ | ---------------------------------------------- |
| 目标   | 一个对象：一个文件或一个目录                   |
| 策略   | 一组 效果（允许或拒绝）× 权限；**拒绝优先**    |
| 来源   | 它是从哪个链接转授来的（对象的根链接没有来源） |
| 创建者 | 创建它的主体                                   |

“整个 `2026/`，但不包括 `2026/raw/`” 就是一个带一条允许和一条拒绝的链接。结果与顺序无关，所以每个节点都得到同样的结果。这是 [Cloudflare API 令牌](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/)的形状，资源就是链接的目标。

### 权限

权限是最小的单位。

| 类别   | 权限                | 允许做什么                                       |
| ------ | ------------------- | ------------------------------------------------ |
| 文件   | `files.list`        | 看到名字                                         |
|        | `files.read`        | 读取内容，并拿到它的密钥                         |
|        | `files.create`      | 新建文件                                         |
|        | `files.change`      | 修改已有的文件                                   |
|        | `files.delete`      | 删除文件                                         |
|        | `files.history`     | 读取旧版本                                       |
|        | `files.watch`       | 监听变化                                         |
| 访问   | `access.view`       | 查看由这个链接转授出去的链接                     |
|        | `access.give`       | 用这个链接在别的命名空间里创建链接，权限不能更多 |
|        | `access.take`       | 收回由这个链接转授出去的链接                     |
| 规则   | `rules.set`         | 为写入设置检查；设定事件的节点列表               |
| 分享   | `share.send`        | 通过分享面板把文件发给另一个 App                 |
| 保存   | `data.keep`         | 保存和转发密文，没有密钥                         |
| 文件夹 | `folder.checkpoint` | 代表所有者签发检查点                             |

### 模板用于给别人授权

一个人给另一个人或一台设备授权时，可以从一个**模板**开始，模板是一组有名字的权限：

| 模板 | 权限                                                                                   |
| ---- | -------------------------------------------------------------------------------------- |
| 只读 | `files.list`、`files.read`、`files.watch`                                              |
| 读写 | 只读，加上 `files.create`、`files.change`、`files.delete`                              |
| 管理 | 读写，加上 `files.history`、`access.*`、`rules.set`、`share.send`、`folder.checkpoint` |
| 中继 | `data.keep`                                                                            |

模板本身没有任何含义，“管理” 只是一组权限。链接里保存的是权限，不是模板的名字。**App 不使用模板**：App 申请的是具体的权限。

### 链接用来做什么

| 什么                    | 链接                                           |
| ----------------------- | ---------------------------------------------- |
| 给某人访问权            | 他命名空间里的一个链接                         |
| 挂载一个文件夹          | 一个指向那个文件夹某个目录的链接               |
| App 的私有数据          | App 命名空间的根，带全部权限                   |
| 交给 App 的文件或文件夹 | App 命名空间里 `/granted/<句柄>/` 下的一个链接 |
| App 之间的分享          | 接收方 App 命名空间里的一个链接                |
| 一个联系人              | 一个指向他的人或组文件夹的链接                 |
| 组的一个成员            | 成员命名空间里一个来自组的根链接的链接         |
| 收件目录                | 一个只有 `files.create` 的链接                 |
| 替你保存数据的辅助节点  | 一个只有 `data.keep` 的链接                    |

## 规则

1. **所有者。** 每个对象有且只有一个所有者：持有它的根链接（没有来源的那个链接）的主体，最初就是创建它的主体。所有者可以是一个组。组也有且只有一个所有者，这条链最终落在某个人的主人根密钥上：优先级最高、永远不能被移除的那把轮换密钥。所有权不能形成环：会形成环的变动不被接受。
2. **转授。** 有 `access.give` 的主体，用自己的一个链接在另一个命名空间里创建新链接，权限相同或更少，目标相同或更小。
3. **收回。** 一个链接被删除时，从它转授出去的链接一起失效。
4. **强移除。** 与它所用的链接被移除同时发生的操作无效。这个操作留在图里，但不产生效果，依赖于它的一切也不产生效果。
5. **检查一次写入。** 主体 P 可以对对象 O 做操作 A，当且仅当在这次写入的因果历史中，存在一条从 O 的所有者出发、经过有效链接、到达 P 持有的某个链接的链，并且链上每一个链接都允许对 O 做 A。这只依赖链接文件和因果顺序，从不依赖时间，所以每个节点都得到同样的结果。
6. **冲突。** 两个操作不能同时成立时，链末端的所有者胜出。
7. **组没有自己的密钥。** “以组的名义” 做的操作，只要签名的密钥能沿链追溯到组的所有者，就是有效的，和 Keyhive 的嵌套组一样。

## 写入检查

对某些文件有 `rules.set` 的主体（通常是 App），可以为写入这些文件设置**检查**，用来实现权限表达不了的规则：大小上限、格式、谁可以在聊天室里发言。每个节点必须得出同样的结论，所以和 CouchDB 的 `validate_doc_update`、Holochain 的验证一样：

1. 检查只回答是或否，并给出理由。它不写任何东西，不发送任何东西，也没有网络。
2. 它拿不到时钟和随机数，依据这次写入的因果历史判断，而不是某个节点当前的状态。
3. 它所用组件的哈希经过签名写在文件夹里；新版本也是一次操作，每次写入用它在图中位置当时有效的版本来检查。
4. 有多个检查时，必须全部同意。没有链，也没有 `next()`。
5. 不检查读取：谁能读，只由密钥决定。

## App

### App 看到什么

- **App 的文件接口是 `wasi:filesystem`（WASI 0.2）。** App 可以使用自己语言的标准库（例如编译到 `wasm32-wasip2` 的 Rust 的 `std::fs`）。
- **它的命名空间以 WASI 预打开目录的形式交给它：** `/`（它的私有数据，实际是这个人文件夹里的 `appdata/<app>/`），以及每一个 `/granted/<句柄>/`。
- 句柄是内核生成的随机名字，不透露文件在哪里。同一个文件在每个 App 里的句柄都不同，所以两个 App 无法知道它们拿到的是同一个文件。句柄一直有效，直到它的链接被收回。

### 在运行时申请

- **清单是 App 最多能申请的东西：** 具体的权限、目标的种类（文件或文件夹），以及可选的类型提示，例如 `image/*`。清单本身不授予任何东西，App 也不能申请更多。
- **App 在需要时才申请。** 它把用户转到内核的选择器（一个 “powerbox”，和 [Sandstorm](https://sandstorm.io) 一样），地址是 `fos.localhost/grant?…`。用户选择一个文件或文件夹，可以取消勾选任何一项权限，也可以拒绝。内核创建链接，再把用户转回来。
- 用户可以随时收回整个链接，或者其中的某几项权限。
- 没有 “照片库” 这样的系统级种类，只有用户选择的文件和文件夹。

### App 之间的分享

和 Android 的 intent 一样：

1. 能接收东西的 App 在清单里声明：
   ```toml
   [[receives]]
   action = "send"
   types = ["image/*"]
   path = "/receive"
   ```
2. 有 `share.send` 的 App 带着一个文件，把用户转到内核的分享面板。内核列出能接收这种类型的 App，由用户选择一个。
3. 内核用分享方自己的链接，在接收方 App 的命名空间里创建一个链接（只读、单个文件、一直有效直到被收回），并带着句柄把用户转到接收方的 `path`。对接收方来说，这是一个普通的 `fetch` 事件。

### 用户自己对 App 数据的访问

默认情况下，App 的数据不在用户的命名空间里，和 Windows UWP 一样。所有者可以给自己一个链接（例如用 `fos folder grant`），之前会提示直接修改可能破坏这个 App。App 仍然会收到 watch 事件，它的检查仍然有效。

## 节点

节点自己的选择（为谁中继、为谁保存备份、提供多少空间）是 `/node/` 下的设置文件，带默认值。持有指向它们的链接的主体可以修改它们。

## 命令行

命令行是所有者的一个入口，和选择器一样。它能看到真实的路径，因为所有者能看到一切。

```
fos app grant <app> <路径> <权限>              例如：fos app grant photos /photos/2026 files.read,files.create
fos app grants [<app>]                        一个 App 的链接，展开每一项权限
fos app revoke <app> <句柄> [<权限>]           收回整个链接，或只收回其中几项权限
fos folder grant <路径> <主体> <模板或权限>
```

## 一个例子

小明有一个文件夹，它的哈希是 `F1`。下面用 `ming` 代表小明的 DID，所以这个文件夹的根是 `/ming/F1/`。它里面的文件是 `/ming/F1/2026/beach.jpg`（O1）、`/ming/F1/2026/cat.jpg`（O2）和 `/ming/F1/private/diary.md`（O3）。这个文件夹是小明创建的，所以他持有根链接。

**1. 小明的命名空间**

```
/photos/        → /ming/F1/    全部权限              ← 根链接
/people/mom/    → 妈妈的文件夹，只读（妈妈给的）
/family/        → 家庭组的文件夹，读写
```

**2. 小明把 2026 年的照片分享给妈妈。** 在妈妈的命名空间里：

```
/来自小明/2026/  → /ming/F1/2026/   files.list, files.read, files.watch
                   来源：小明的 /photos/   创建者：小明
```

妈妈看到的 `/来自小明/2026/cat.jpg`，和小明的 `/photos/2026/cat.jpg` 是同一个对象 O2，只是另一条路径。她到不了 `private/`。

**3. 照片 App 申请照片。** 小明选择 `/photos/2026/`，并额外勾选 `files.create`。在 App 的命名空间里：

```
/              → 小明文件夹里的 appdata/photos/   全部权限
/granted/7Hq2/ → /ming/F1/2026/   files.list, files.read, files.watch, files.create
                 来源：小明的 /photos/
```

App 读取 `/granted/7Hq2/cat.jpg`（O2），不知道它就是 `/ming/F1/2026/cat.jpg`，也不知道它在小明的 `/photos/` 下。它上传 `dog.jpg` 时，新建了文件 `/ming/F1/2026/dog.jpg`，小明和妈妈立刻都能看到。

**4. 照片 App 把 `cat.jpg` 分享给聊天 App。** 在聊天 App 的命名空间里：

```
/granted/K9pa/cat.jpg → /ming/F1/2026/cat.jpg   files.read, files.watch
                        来源：照片 App 的 /granted/7Hq2/
```

O2 现在有四条路径：

| 主体     | 路径                     | 权限                 |
| -------- | ------------------------ | -------------------- |
| 小明     | `/photos/2026/cat.jpg`   | 全部                 |
| 妈妈     | `/来自小明/2026/cat.jpg` | 列表、读、监听       |
| 照片 App | `/granted/7Hq2/cat.jpg`  | 列表、读、监听、新建 |
| 聊天 App | `/granted/K9pa/cat.jpg`  | 读、监听             |

**5. 检查写入。** 照片 App 的上传有效：从小明（所有者）到照片 App 的链接，这条链带着 `files.create`。妈妈的上传无效：她唯一的链接没有 `files.create`。聊天 App 不能修改 `cat.jpg`：它的链接没有 `files.change`。

**6. 收回。** 小明收回照片 App 的链接。从它转授出去的聊天 App 的链接一起失效；妈妈的链接来自小明的根链接，不受影响。照片 App 在同一时间、在另一台设备上做的上传无效（强移除）。两个 App 都会在 `/granted/` 下收到 watch 事件。

**7. 组。** 家庭组的文件夹 `G` 的所有者是妈妈，成员是小明和爸爸。家庭相册 `F2` 的所有者是 `G`。小明和爸爸各持有一个来自 `G` 的根链接的读写链接。小明写入时，验证的链是 `G`（所有者：妈妈）→ 小明的链接。冲突时，链末端的所有者，也就是妈妈，胜出。

**8. 密钥。** 密钥跟着根路径（见[数据](../data/#跟着路径的密钥)）：小明有 `F1` 的密钥；妈妈和照片 App 有 `2026/` 的密钥，推不出 `private/` 的密钥；聊天 App 只有 `2026/cat.jpg` 的密钥。小明收回照片 App 的链接时，只需要更换 `2026/` 的密钥，新密钥发给小明和妈妈。

## 一套逻辑覆盖全部

| 什么                       | 怎样实现                                       |
| -------------------------- | ---------------------------------------------- |
| 任何人对任何东西的访问     | 一个带权限的链接                               |
| 挂载、联系人、收件目录、组 | 链接                                           |
| 用户为 App 选择文件        | 内核创建一个链接                               |
| App 分享给另一个 App       | 一个由分享方的链接转授出来的链接               |
| 命令行授予权限             | 一个链接                                       |
| App 得知自己的链接         | 它的命名空间，以及 `/granted/` 上的 watch 事件 |
| App 的规则                 | 创建和收回链接，以及检查                       |
| 收回                       | 删除一个链接，连同由它转授出去的部分           |
| 谁胜出                     | 链末端的所有者                                 |
| 谁能读                     | 拥有这条路径的密钥的人                         |
