## 为什么没有排序节点

原型给每个文件夹一个排序节点，由它把所有写入排成一个顺序。但在人与人之间的网络里，不能假设任何节点一直在线、永不变化：笔记本会休眠，手机会换网络，家里的盒子会断电。只有一个排序节点时，它不在，谁都写不了。

这是绕不过去的：没有一个一直在线的节点，也没有多数节点在线时，系统不可能既随时接受写入，又让每个读者都看到最新的数据（CAP 定理）。我们选择随时接受写入。数据的正确性来自合并，而不是来自所有者：

- **任何节点随时都能写，离线也能写。**
- **只要拿到同样的操作，不论顺序如何，所有节点都会得到同样的状态。**
- **所有者只是一种优化**（为了更快、少做重复工作），从来不是数据正确的前提。

## 数据模型

### 签名日志组成的因果图

- 每个写入者（一个节点或一个 App，按它的密钥）有自己的**只追加日志**。每条记录由写入者签名，用哈希指向同一条日志里的前一条记录，并指向它所依赖的其他日志里的记录。
- 所有日志合在一起，组成一个**因果图**（DAG）：一条记录排在它所指向的一切之后。
- 一条记录有一个很小的**头部**（写入者、签名、在日志中的位置、依赖、正文的哈希）和一个**正文**。两者分开保存，所以可以删掉正文，而哈希链仍然完整。

这和 [p2panda](https://p2panda.org) 的格式非常接近：Ed25519、BLAKE3、CBOR，每个作者一条日志，头部和正文分开。我们以它的格式为参照。

### 空间是一个扁平的键空间

在一个空间内部，数据是一个**扁平的键集合**，就像 S3，而不是一棵由目录节点组成的树：

- 键是一个路径，例如 `/photos/2026/a.jpg`。“目录” 只是一些键的公共前缀，列目录就是按前缀查找。
- 没有移动操作。改名就是新建一个键、删除旧的键。这很便宜：内容是按哈希命名的块，不复制任何数据。
- 需要空目录时，用一个标记键表示。
- 键是 NFC 形式的 UTF-8，用 `/` 分隔，区分大小写；不允许 `.` 和 `..`；有长度上限。

为什么不用树：目录可以移动时，并发的移动会形成环（A 移进 B，同时 B 移进 A）；而且每个节点必须对 “每次写入和每次授权发生时，节点在树的哪个位置” 得出相同的结论。这非常难做对，还会在没人要求的情况下改变访问权限。在扁平的键空间里，权限跟着路径走，而路径永远不会因为别的操作而改变。

用户看到的仍然是一棵树，由视图组成：持有者把自己拿到的授权挂载在自己选的名字下。空间是同步、所有者和密钥的大单位，就像 S3 的 bucket，很少变化。

### 每个键各自合并

- 对不同键的写入永远不会冲突。
- 对同一个文件的并发写入会**并排保存为多个版本**。系统绝不会在用户不知情的情况下选出一个胜者（见[冲突](#冲突人和开发者会看到什么)）。
- 内容是 CRDT 的文件（见[内核给 App 提供什么](#内核给-app-提供什么)）由内核合并，而不是保留为多个版本。
- 没有流，也没有键值存储：一切皆文件。一串记录（聊天、动态）就是一个目录，每条记录一个小文件，文件名按时间排序且永不重复。不同的文件永远不会冲突。

## 权限：授权，采用强移除

### 在前缀或文件上授予具体的权限

访问就是一项**授权**：把具体的权限（例如 `files.read` 或 `access.give`）授予一个 App、一个人、一台设备或一个组，作用在一个空间中名字的前缀上（一个 “区域”，和 [Willow 的 Meadowcap](https://willowprotocol.org/specs/meadowcap/index.html) 一样），或者按 ID 作用在一个文件上。授权可以转授给别人，但只能缩小。每个节点不联网就能检查一次写入。没有授权引擎：规则由管理文件的 App 制定。完整的模型（内容、文件、空间、主体、授权、视图和事件）见[模型：空间、授权与视图](../access/)。

### 移除和写入同时发生时

这是没有排序节点时，访问控制中最难的问题。我们采用 [p2panda-auth](https://p2panda.org/2025/07/28/access-control.html) 称为**强移除**的规则：

- 一个人的权限被收回时，他在移除**同时**做的所有操作都无效。这些操作留在图里，但不产生效果；依赖于它们的操作也无效。
- 它只依赖因果顺序，不依赖时钟，每个节点都得出同样的结论。

强移除有一个坏情况：两个管理员同时移除对方，两人都会被移除，群组可能从此没有管理员。所以每个身份都有一把**主人根密钥**：它的 [`did:fos`](../identity/) DID 中优先级最高的轮换密钥。它永远不能被移除，在任何冲突中都胜出。家人和朋友通过它下面的群组获得权限。

强移除是内核唯一的规则，每个节点都一样。一批文件需要不同的规则时，由管理它们的 App 来提供（见[模型](../access/)）。

**授权永远不使用时间。** 时钟出错、或者谎报时间的节点，不能因此获得或保住权限。

## 一致性

### 保证什么

- **所有节点最终得到同样的状态**（强最终一致性）。
- **在同一个会话里，你总能看到自己的写入，也永远不会看到比之前更旧的数据**（读己之写、单调读）。
- **在设备之间，**都在线时几秒内就能看到对方的写入，但不是立刻。

### 粘性和 bookmark

我们采用 [Cloudflare D1 的 Sessions API](https://developers.cloudflare.com/d1/best-practices/read-replication/) 的做法：

- **粘性：** 一个会话固定由一个节点处理，通常就是你设备上的节点。这个节点会立即把自己的写入放进自己的视图，所以你一定看得到。
- **bookmark：** 每个回应都带一个 `Fos-Bookmark` 头，内容是生成这个回应时所依据的图的头部。App 在下一个请求里把它带回来。还没看到这些记录的节点会先等待，或者把请求转给已经看到的节点。

### 需要协调的规则

有些规则无法靠合并来保证，因为每个节点都是独自决定的：必须唯一的名字、不能重复的预订、不能小于零的数字。对于这些少数情况，有一条**权威路径**：App 声明某次写入必须由一个指定的节点同意（默认是主人的一个节点）。联系不上这个节点时，写入失败，绝不会悄悄保存下来以后再合并。

## 冲突：人和开发者会看到什么

CRDT 保证所有设备最终得到同样的数据，但不保证这份数据是任何人想要的。冲突并没有消失，只是被一条固定的规则解决了。仍然会发生的有：

- **同一个值被同时写。** 用 “最后写入者胜出”，一次写入会丢失；用多值寄存器，两个值都保留，由 App 来选。
- **同时在同一处写文本。** 有些算法会把两次写入的字母交错混在一起。较新的算法，例如 [Fugue](https://arxiv.org/abs/2305.00583)，把这种情况降到很低。
- **移动。** 列表里的并发移动会产生两份，树里的并发移动会形成环。（这也是选择扁平键的理由之一。）
- **删除和编辑同时发生。** 大多数情况下删除胜出，编辑丢失。
- **语义上的规则**（名字唯一、重复预订、小于零）。CRDT 看不到这些，见[需要协调的规则](#需要协调的规则)。

### 默认做法

| 数据           | 默认                                                                             |
| -------------- | -------------------------------------------------------------------------------- |
| 整个文件       | 保留所有版本，绝不悄悄选出胜者；系统显示 “有 N 个版本”，让用户选择               |
| App 的数据文件 | 和文件一样；App 需要合并时，用 CRDT 文件（例如每个字段 “最后写入者胜出” 的映射） |
| 文档（富文本） | 文本 CRDT（基于 Fugue），保留完整历史；写作类内容支持草稿和审阅                  |
| 语义上的规则   | 权威路径，或者用户能看到的修复                                                   |

### 用户看到什么：简单页面和高级页面

内核的界面（`fos.localhost`）用同样的方式，为所有 App 和文件显示冲突和回滚：

- **简单页面**告诉用户该做什么：有并排的多个版本时，“保留我的”、“保留对方的” 或 “都保留”；数据被回滚时，用一句话说明原因（“因为 Ann 的权限被收回，她的 3 处修改已被撤销”）；离线时的修改被重新应用时，一句话加一个链接。
- **高级页面**给想弄清楚发生了什么的人：文件的完整历史和时间线，按作者和设备筛选；任意两个版本之间的差异；恢复到任意版本；因果图；以及检查点或强移除为什么让某个操作无效。

### 内核给 App 提供什么

- **内容是 CRDT 的文件**，由内核合并：寄存器（最后写入者胜出、多值）、映射、计数器、文本、可移动列表、可移动树。CRDT 文件是文件的一种，而不是单独的存储。它们基于同一个库 [Loro](https://github.com/loro-dev/loro)（MIT），它有可移动列表和可移动树，并能裁剪旧的历史。采用之前要先测量它的代价。
- **完整保留历史**（在保留策略之内），任何 “输掉” 的写入都能找回。
- **统一的冲突接口和系统级的版本视图**，而不是每个 App 各做一套。
- 写入被接受之前的**写入检查**，以及合并之后的 **watch 事件**，App 可以在这里修复违反它规则的内容（见[模型](../access/#写入检查)）。
- **权威路径**，作为可以替换的策略。

## 不会无限增长的存储

数据随时间增长、而不是随人们关心的内容增长，是软件难以自建的一个主要原因。所以这是一条规则：**默认情况下，任何类型的数据都不能无限增长。** 每类数据都有所有者、保留期限，以及空间不够时的处理办法。

| 数据                 | 怎样保持有界                                     |
| -------------------- | ------------------------------------------------ |
| 当前内容             | 只随人们添加的内容增长                           |
| 旧版本               | 保留策略，越久越稀疏                             |
| 日志、头部、删除标记 | 在检查点压缩                                     |
| 缓存和索引           | 有预算；最少使用的先淘汰；从不备份；随时可以重建 |
| 为别人保存的数据     | 每个人一个配额；中继和信箱里的数据到期删除       |

### 保留策略：越久越稀疏

和 Time Machine、restic 的 `forget --keep-…`、Syncthing 的 staggered 版本一样。默认：

- 最近 24 小时：每小时保留一个版本；
- 最近 30 天：每天保留一个版本；
- 更早：每周保留一个版本，有上限。

这是每个空间可以单独设置的策略。删除的文件进入回收站，一段时间后清空。

### 按内容分块

文件在由内容决定的位置切成块（按内容分块，和 restic、borg 一样），每块按 BLAKE3 哈希命名。新版本只保存变化了的块；两个文件中相同的内容只保存一次；同步时只传缺少的块。所以旧版本的代价大约等于变化的字节数，而不是文件的大小。

### 检查点：更小的日志和最终确定的历史

空间的所有者（它的所有者链末端的那个），或者有 `space.checkpoint` 的主体，会不时签发一个**检查点**（这是策略，例如每天一次，在所有者的某台设备在线时）。有权签发的人都长时间不在线时，检查点暂停，压缩也随之暂停：数据仍然正确，只是暂时多占一些空间。检查点声明：“到这些头部为止的状态已经最终确定。”

- **压缩。** 检查点之前的历史变成一个快照：只保留保留策略要留的记录，删除标记被清除，访问控制只保留当时的成员，就像 Kafka 按键压缩日志那样。新节点直接从签名的快照开始。旧的正文可以先删除，很小的头部在下一个检查点再删除。Loro 也能用同样的方式裁剪历史（浅快照）。
- **最终确定。** 检查点之后才到达、却声称更早的记录，不会被接受。否则，一台被盗的设备可以伪造 “早先” 的写入，没有人能把它和一个迟到的诚实写入区分开。
- **长时间离线的设备。** 它早于检查点的修改，会像 `git rebase` 那样作为新记录重新放到最上面，并告诉用户。和其他修改冲突的地方，结果是并排的多个版本。什么都不会丢，但也绝不悄悄合并。

### 看得见的预算

- `fos node status` 显示空间都用在了哪里：内容、旧版本、元数据、缓存，以及为别人保存的数据。
- 用户可以设定预算。快满时，内核按这个顺序腾出空间：先淘汰缓存，再让旧版本更稀疏，再停止接收别人的新数据，最后才告诉用户。用户当前拥有的内容，内核永远不会删除。
- App 需要保留的数据是家目录里的文件，派生的数据是每个节点上的缓存文件。缓存文件计入预算，可以随时被删除。

## 加密

### 前向保密，以及它在哪里有意义

前向保密的意思是：今天密钥被盗，过去的数据仍然安全。对**仍然保留着**的数据，这不可能做到：拿到今天密钥的人，能读你能读的一切。Keyhive 这类使用 CRDT 的系统正是因此放弃了它。前向保密在另外三个地方有意义，我们在那里保留它：

| 场景                 | 做法                                                             |
| -------------------- | ---------------------------------------------------------------- |
| 已删除或已压缩的数据 | **随数据一起销毁密钥**，任何地方的副本都失去用处                 |
| 网络传输             | libp2p 的 Noise 已经提供                                         |
| “用过即焚” 的聊天    | 用户需要时，为这段对话使用双棘轮（代价是新设备读不到之前的消息） |

### 跟着前缀的密钥

一项授权可以作用在空间深处的某个前缀上，甚至某一个文件上。一项读授权必须只交出那一部分的密钥。所以密钥跟着名字的前缀走，采用 Cryptree（Grolimund 等人）和 Tahoe-LAFS 的做法：

1. **每个块用一个随机的数据密钥加密。** 数据密钥用文件所在前缀的密钥加密保存（密钥包装）。
2. **前缀的密钥由上一层前缀的密钥经单向函数推导出来。** 拥有空间 `S1` 中 `2026/` 的密钥的人，能推导出它下面一切的密钥，但推不出整个空间或 `private/` 的密钥。
3. **读授权交出它所作用对象的密钥。** 妈妈有一项作用在 `2026/` 上的授权，就拿到 `2026/` 的密钥；一个只拿到单个文件授权的 App，只拿到这个文件的数据密钥。
4. **收回一项读授权时，** 只需更换它所能到达的那一部分的密钥（并重新包装其下的数据密钥，数据本身不用重新加密）。新密钥发给仍对这一部分有读授权的所有人：这就是入侵后安全，也会定期这样做。
5. **删除就是销毁密钥**（crypto-shredding）。文件被删除、被保留策略淘汰、或在检查点被压缩掉时，它的数据密钥被销毁。朋友节点上和备份里的密文副本从此只是一堆字节。我们无法强迫朋友的节点删除你的数据，但这样一来，删不删已经无所谓了。

### 分发密钥：HPKE

创建或修改一项读授权的设备，用 **HPKE**（RFC 9180）把它所作用对象的密钥，分别发给对它有读授权的每一个主体的每一台设备。

- 两次变动同时发生时，两个密钥都能用来读；新的写入按固定规则选用其中一个。不需要排序节点。
- 代价是每台设备一条 HPKE 消息。一个 10 人、每人 3 台设备的家庭空间，就是 30 条消息，而且成员变动很少发生。
- **弱点：** 设备用自己的 HPKE 密钥接收密钥。如果这把密钥以后被盗，而有人保存了加密后的密钥，他就能打开它们。所以**每台设备要定期更换自己的 HPKE 密钥，并销毁旧的。**

我们比较了三种群组密钥协商协议：

| 协议                                 | 为什么现在不用                                                     |
| ------------------------------------ | ------------------------------------------------------------------ |
| MLS（RFC 9420）                      | 每个纪元必须恰好有一个提交，所以需要排序节点                       |
| DCGKA（Weidner、Kleppmann 等，2021） | 最契合，但它唯一的 Rust 实现（p2panda 的）在审计后还有未修复的问题 |
| BeeKEM（Keyhive）                    | 也契合，但还没准备好（“不要用于生产”），没有审计                   |

HPKE 简单，用标准部件，对小群组足够。等 DCGKA 或 BeeKEM 准备好并经过审计，我们可以升级过去，获得更强的前向保密。所用的 crate 是 [`hpke`](https://github.com/rozbb/rust-hpke) 0.15（纯 Rust，能编译成 WebAssembly）。在用于真实数据之前，会先经过外部的安全审计。

## 实现：新的内核

本页、[模型](../access/)和 [App 作为 Worker](../workers/) 的设计，和原型相差太远，无法一步一步地修改过去，而两者之间的中间状态没有任何意义。所以内核重新编写：

- **保留：** `fos-core`（格式）、`fos-id`（`did:fos`）、作为测试方式的 `fos-sim` 仿真、`.app` 文件、网关，以及 `wasi:http` 运行时。
- **新写：** 因果图中的签名日志、名字扁平的空间、ID 固定的文件、授权和视图、强移除、写入检查、分块、检查点、跟着前缀的密钥、App 的 `wasi:filesystem`，以及 watch。
- **顺序：** 先在 `fos-sim` 中实现数据模型，从第一个测试 “节点离线时也能读到自己的写入” 开始；然后是存储、网络和运行时；最后去掉旧的 `fos-fs`、`fos-sync` 和引擎。
