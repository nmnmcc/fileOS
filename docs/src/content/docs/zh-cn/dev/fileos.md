## 一句话

**内核只保存事实：数据、签名、密钥和传输。所有规则和所有功能，都是用户自己选的 WebAssembly 代码：授权引擎决定规则，App 提供功能。**

## 为什么只要一个底层

一个系统如果有很多互相独立的概念（群组、条目、授权、令牌、副本、中继、插件），每个新功能都会带来一个新概念，每个概念都要有自己的代码、自己的测试和自己的同步规则。

fileOS 只有一个底层，其他一切都在它上面构建。它最初的想法来自 IPFS：文件按哈希命名。但它比 IPFS 小得多，因为它是为个人和家庭的电脑设计的，而不是为全球网络设计的：

- 没有全局的内容 DHT。节点通过人与人的关系找到彼此。
- 默认什么都不公开。
- 节点不会保存任何它没有同意保存的东西。

## 五个概念

整个系统只有五个概念，其他一切都由它们组合而成。

| 概念   | 是什么                                 |
| ------ | -------------------------------------- |
| 文件夹 | 一条签名日志加上一组 blob              |
| 密钥   | 人、设备、节点和 App 都是一个密钥      |
| 节点   | 保存文件夹、同步文件夹、运行代码的地方 |
| 引擎   | 节点的访问规则，由节点主人选择（WASM） |
| App    | 读写文件夹的程序（WASM）               |

用户熟悉的东西都由这五个概念组合而成：

| 你看到的       | 实际是                         |
| -------------- | ------------------------------ |
| 群组           | 多个节点都同意保存的文件夹     |
| 聊天           | 文件夹里的一个流               |
| 相册、共享网盘 | 文件夹里的文件                 |
| 备份           | 一个保存文件夹密文的节点       |
| 中继、离线信箱 | 一个节点暂时替别人保存一些记录 |
| 使用别人的节点 | 那个节点的引擎同意了你         |
| 安装 App       | 把一个 App 文件夹放进 `/apps/` |
| 更新 App       | 同步这个文件夹                 |
| 更换访问规则   | 更换你节点的引擎               |
| 迁移到新服务器 | 让一个新节点同步你的文件夹     |

## 分层

```
┌───────────────────────────────────────────────┐
│ App (WASM)   照片 聊天 密码库 搜索 登录 …      │
├───────────────────────────────────────────────┤
│ 引擎 (WASM，每个节点一个，由主人选择)          │
├───────────────────────────────────────────────┤
│ WIT: fos:fs fos:watch fos:authz + wasi:http … │
├───────────────────────────────────────────────┤
│ 内核：文件系统 · 签名和哈希 · 同步 ·           │
│       密钥 (MLS) · App 运行时 · 网关           │
├───────────────────────────────────────────────┤
│ wasmtime · libp2p · 磁盘                      │
└───────────────────────────────────────────────┘
```

内核里没有任何"应该怎样"。它不知道照片、聊天、密码是什么，不知道群主是谁，也不知道 Bitwarden、CalDAV 或 OpenID Connect。

## 文件系统

### 文件夹

**文件夹**是同步、排序、授权和加密的基本单位。

- 文件夹的 ID 是创建它的那条记录的哈希，永远不变。
- 文件夹的全部状态都来自**一条签名日志**。
- 文件内容是 blob，按哈希命名。这部分和 IPFS 相同。
- 文件夹可以在某个路径上**挂载**另一个文件夹，这样就形成一棵树。

一个人的根目录、一个群组、一个相册、一个 App，都是文件夹。

### 三种对象

| 对象 | 作用                        | 例子                 |
| ---- | --------------------------- | -------------------- |
| 目录 | 名字到对象的映射            | `/photos/2026/`      |
| 文件 | 指向一个 blob，保留所有版本 | 照片、文档           |
| 流   | 只能追加的记录序列          | 聊天、密码条目的变更 |

### 写操作就是日志里的记录

```
put(path, hash) · delete(path) · append(path, data)
mount(path, folder-id) · policy(bytes)
```

每条记录都由写入者签名。内核不解释 `policy(bytes)` 的含义，由引擎来读（见下文）。

### 顺序

- 文件夹的日志里写着一个**排序节点**。排序节点可以把这个工作交给另一个节点。
- 其他写入者把写操作发给排序节点，由它确定顺序。这个顺序就是文件夹的**主线**。
- **流**：两次追加之间不会有冲突。
- **文件**：顺序上靠后的写入成为当前版本，旧版本留在历史里，所以什么都不会丢。
- 离线的节点把写操作放进队列，以后再发出去。

排序规则是一种策略。某个文件夹可以换成别的规则，比如 CRDT。

### 路径

```
/<key>/...                  一个人的根
/<key>/groups/family/       挂载的共享文件夹
/<key>/apps/Photos.app/     挂载的 App
/<key>/appdata/<app-id>/    App 的私有数据，会同步
/local/<app-id>/            App 在本节点的缓存，不同步
/node/                      本节点的设置和引擎
```

## 授权引擎

### 内核保存事实，引擎决定规则

| 内核（机制，不能替换）     | 引擎（策略，WASM，可以替换）         |
| -------------------------- | ------------------------------------ |
| 验证签名：这条记录是谁写的 | 判断这个人能不能做这件事             |
| 验证哈希：内容没有被改过   | 解释 `policy` 记录的含义             |
| 询问引擎，并执行它的结论   | 回答谁能读、哪些节点能保存某个文件夹 |
| 把密钥交给引擎指定的读者   | 决定谁能用这个节点、能用多少         |
| 记录日志、同步、计量资源   | 决定每个 App 能用什么                |

"是谁"是事实，所以放在内核里。"能不能"是规则，所以放在引擎里。

### 每个节点一个引擎，不加限制

每个节点运行主人选择的引擎，内核对它**不加任何限制**：只要主人允许，它可以读时钟、访问网络、调用 App。控制节点的人本来就能让节点做任何事，系统公开承认这一点，不假装自己能阻止他。

引擎和其他 App 一样，就是 `/node/Engine.app/`。要换规则，就换这个文件夹。

### 任何代码都做不到的事

在你自己的节点上，你可以做任何事。但有三件事任何代码都做不到。它们来自数学，而不是规则：

1. 不能用别人的密钥生成签名。
2. 没有密钥就读不到加密的数据。
3. 不能让别人的节点做任何事。

所以别人的数据放在你的节点上是安全的。保护它的是加密，而不是系统管住你。

### 共享文件夹

**共享文件夹就是：多个节点，各自用自己的引擎，都同意接收这个文件夹的写入。** 没有谁能强迫别的节点。

节点之间意见不同时，各自的副本就会**分叉**。举个例子：

- Alice、Bob 和 Carol 共享 `/family/`，Alice 是创建者。后来 Alice 把 Dave 移出了群组。
- Alice 和 Bob 的节点用默认引擎，它们认这次移出，所以不再接收 Dave 的写入。
- Carol 给自己的节点换了一个引擎，规则是"Dave 是我朋友，他写的我都收"。
- Dave 往文件夹里放了一张照片。Carol 能看到，Alice 和 Bob 看不到。

分叉有两种：

- **只是过滤。** 一个节点收了某条记录，另一个节点没收。这就像同一个邮件线程，两个人的垃圾邮件过滤规则不同，但他们仍然在同一个线程里。
- **状态不同。** 后面的记录依赖于只有部分节点收下的那条记录，或者节点之间对成员、当前版本的看法不同。这时两个副本会各走各的路，就像 git 的 fork。

排序节点维护主线。如果它的引擎不收 Dave 的照片，这张照片就进不了主线。Carol 可以在自己的节点上留着它，但它只是 Carol 自己的旁支。如果 Carol 的引擎拒绝了主线上的某条记录，她的副本就停在那里。她可以等，也可以另开一条线。

让分叉的影响尽量小：

1. 记录之间不需要依赖时，就不要互相依赖。聊天消息和照片各自独立，只有成员变化和文件版本才依赖主线的顺序。
2. 让用户看到分叉，比如"你的副本和主线有 3 条记录不同"。用户可以选择跟随主线、保留自己的旁支，或者把它变成一个新文件夹。
3. 大多数时候不会有分叉。大家都用默认引擎，或者用规则一致的引擎时，每个副本都一样。

**系统不强制大家一致，但默认就是一致的。谁改了规则，谁的副本就和别人不同，而这是他自己的选择。**

### 默认引擎：capability

大多数人会用默认引擎，它基于 capability：

```
capability = {
  issuer:   签发它的密钥
  audience: 接收它的密钥（人、设备、节点或 App）
  resource: 文件夹 ID 加路径前缀
  ability:  read | write | append | grant | store | serve | use-node
  limits:   截止时间、配额、对象类型
  proof:    上一级 capability（签名链）
}
```

- 一个文件夹的授权链，根是创建这个文件夹的密钥。
- capability 可以转给别人，但权限只能变小，不能变大。
- 收回 capability 时，在文件夹日志里写一条 `policy` 记录，它会随文件夹一起同步。

有了 capability，熟悉的概念都变得很简单：

| 概念           | 用默认引擎实现                                     |
| -------------- | -------------------------------------------------- |
| 群组成员       | 持有这个文件夹的 `read`、`write` 或 `append`       |
| 群主           | 持有 `grant`                                       |
| 节点保存文件夹 | 节点的密钥持有 `store`                             |
| 朋友帮你备份   | 朋友的节点有 `store` 但没有 `read`，所以只看到密文 |
| 中继、离线信箱 | 带截止时间和配额的 `store`                         |
| 使用别人的节点 | 那个节点的密钥给你 `use-node`，带配额              |
| App 能做什么   | 你给 App 的一个更小的 capability                   |

别人也可以写其他引擎，比如：

| 引擎         | 规则                                             |
| ------------ | ------------------------------------------------ |
| 角色（RBAC） | 主人、成员、访客。适合家庭和小团队               |
| 多签         | 一个改动需要 n 个人中的 k 个签名。适合家庭密码库 |
| 投票         | 群组成员投票决定加人或移出某人                   |
| 遗产         | 一段时间没有活动后，权限交给指定的人             |

### 引擎接口

```wit
interface authz {
  // 新文件夹的状态。
  init: func(folder: string, creator: key) -> list<u8>;
  // 读取一条 policy 记录，更新引擎自己的状态。
  apply: func(state: list<u8>, author: key, policy: list<u8>) -> result<list<u8>, string>;
  // 判断一个操作是否允许。
  check: func(state: list<u8>, principal: key, op: op) -> decision;
  // 内核需要的查询。
  readers: func(state: list<u8>) -> list<key>;   // 用来分发密钥
  storers: func(state: list<u8>) -> list<key>;   // 用来同步
  // 给 `to` 在 `path` 上一些能力的 policy 记录。
  grant: func(to: key, abilities: list<ability>, path: string) -> list<u8>;
}
```

有了 `grant`，内核不需要知道 policy 记录的格式，也能给 App 或别人授权。完整接口见 `wit/fos.wit`。以后内核会缓存结果：同一个状态、同一个人、同一个操作，只算一次。

## 加密

- 每个文件夹有一个内容密钥，文件夹的读者通过 MLS（RFC 9420）共享它。
- 只有 `store` 的节点永远拿不到密钥，只保存密文。
- 移出一个读者时，密钥会更换。

所以"谁能读"不是靠拒绝请求实现的，而是靠**谁拿到密钥**。引擎给出读者名单，内核负责加密。

## 同步和网络：libp2p

网络部分我们用 [libp2p](https://libp2p.io)，不自己造。它经过了充分验证，用得很广，而且能满足我们的需要：

| 我们需要的           | libp2p 提供的                                  |
| -------------------- | ---------------------------------------------- |
| 节点身份             | PeerId，由节点的 ed25519 密钥生成              |
| 加密传输             | TCP 加 Noise 和 Yamux（QUIC 以后再加，见下文） |
| 不需要公网 IP 和域名 | AutoNAT、DCUtR（打洞）、Circuit Relay v2、UPnP |
| 为朋友中继（互助）   | Circuit Relay v2，由引擎决定帮谁               |
| 发现家里网络中的节点 | mDNS                                           |
| 实时推送变更         | gossipsub，每个文件夹一个 topic                |
| 我们自己的同步协议   | request-response 和 stream                     |
| 浏览器和手机         | WebTransport、WebRTC、WebSocket                |

我们用 libp2p，但不用其中属于 IPFS 的部分：

- **不用 bitswap，也不用全局内容 DHT。** 节点只从保存这个文件夹的节点获取 blob。
- **完全不用 DHT。** 节点通过任何人都能部署的会合节点，以及熟人的节点找到。见[身份与查找节点](../identity/)。

以下部分仍然由我们自己做，因为它们就是 fileOS 本身：文件夹日志的同步协议、记录的排序，以及用 MLS 分发密钥。

同步的方式：

- 节点之间互相发送各自文件夹日志的末端，然后获取自己缺少的记录。
- 节点可以按哈希，从任何保存这个文件夹的节点获取 blob。
- 每个节点的引擎决定接收哪些记录。
- 同步协议是 sans-IO 的，不依赖 libp2p。`fos-net` 把它接到 libp2p 上，`fos-sim` 把它接到内存传输上。

## App 运行时：wasmtime

运行时我们用 [wasmtime](https://wasmtime.dev)，不自己造：

| 我们需要的             | wasmtime 提供的                       |
| ---------------------- | ------------------------------------- |
| App 和引擎的接口       | Component Model 和 WIT                |
| 资源限制               | fuel 或 epoch 中断、`ResourceLimiter` |
| 大量 App 实例          | pooling allocator                     |
| 启动快                 | 预编译的 `.cwasm` 保存在 `/local/`    |
| 配合异步 I/O           | async 支持                            |
| 不能 JIT 的平台（iOS） | Pulley 解释器                         |

### App 接口（WIT）

能用 WASI 0.2 标准的地方就用标准，这样 WASI 的工具和库都能直接用：`wasi:http`、`wasi:clocks`、`wasi:random`、`wasi:logging`。我们**不用** `wasi:filesystem`，因为它是 POSIX 语义。文件系统的接口由我们自己定义。

内核提供给 App 的接口（导入）：

| 接口                                         | 作用                                             |
| -------------------------------------------- | ------------------------------------------------ |
| `fos:fs`                                     | 读、写、追加、列目录，只限 App 有权使用的路径    |
| `fos:watch`                                  | 某个路径变化时收到通知                           |
| `fos:cap`                                    | 查看调用者是谁；申请或转出 capability            |
| `fos:kv`                                     | 只在本节点的有序键值存储，用来放索引             |
| `wasi:http`                                  | 对外请求，只能访问 manifest 里声明并被允许的主机 |
| `fos:crypto`                                 | 用 App 实例的密钥签名，永远拿不到用户的密钥      |
| `wasi:clocks`、`wasi:random`、`wasi:logging` | 基础功能                                         |

App 提供给内核的接口（导出）：

| 接口                     | 内核什么时候调用             |
| ------------------------ | ---------------------------- |
| `on-change(path, entry)` | App 监听的路径发生变化时     |
| `handle-http(request)`   | 请求命中 manifest 里的路由时 |
| `run-job(name)`          | 定时任务或后台任务           |

### App 的规则

- App 在事件到来时运行，没有线程，由内核安排运行时间。
- 每个实例都有内存、fuel 和时间的限制，资源从 `use-node` 的配额里扣。
- **App 之间只通过文件系统协作。** 一个 App 写，另一个 App 监听，没有别的通信方式。
- 我们自己的 App 和别人的 App 用同样的接口、同样的沙箱，我们的 App 没有特殊通道。

## App 包

App 就是一个文件夹，和 macOS 一样：放在那里就能用，删掉就没了。没有包管理器，也没有另外的"已安装"列表。只有一个 `.wasm` 文件是不够的，所以我们向 macOS 的 `.app` 包学习。

### macOS 的 `.app` 是怎么组织的

```
Photos.app/
  Contents/
    Info.plist                  ID、版本、主程序、文件类型、URL scheme、
                                申请权限时显示的理由
    MacOS/Photos                主程序（可以包含多种 CPU 架构的代码）
    Resources/                  图标、界面文件、en.lproj/ zh-Hans.lproj/ …
    Frameworks/                 App 自带的库
    PlugIns/                    扩展（.appex），每个扩展本身也是一个包
    XPCServices/                辅助程序，权限比主程序小
    _CodeSignature/CodeResources  包内每个文件的哈希（封条）
```

围绕它，macOS 还有：entitlements（App 能做什么，签进程序里）、公证（Apple 检查 App）、Gatekeeper（打开 App 前检查）、Launch Services（记录哪个 App 打开哪种文件）和容器（`~/Library/Containers/<id>/`，存放 App 的私有数据）。

### fileOS 的 `.app`

```
Photos.app/
  manifest.toml              对应 Info.plist 和 entitlements
  bin/
    app.wasm                 主组件
    thumbnailer.wasm         辅助组件，权限更小（对应 XPCServices）
  lib/
    exif.wasm                共享组件（对应 Frameworks）
  extensions/
    Thumbnail.ext/           扩展（对应 .appex）：为 image/* 生成缩略图
      manifest.toml
      ext.wasm
    SearchExtractor.ext/     对应 Spotlight 导入器：从照片里提取用于搜索的文字
  ui/                        网页界面
  resources/
    icon.svg
    locales/en-us.toml
    locales/zh-cn.toml
```

不需要 `_CodeSignature/`。App 是一个文件夹，而文件夹就是一条按哈希引用每个文件的签名日志。发布者签名日志的末端，这就是封条，我们不需要另外做任何事。

### manifest

```toml
id       = "photos"           # 加上发布者密钥就是唯一 ID，不需要域名
name     = "Photos"
version  = "1.4.0"            # 给人看的版本号
build    = 142                # 构建号
requires = "fos:app@1"        # 需要的 WIT 版本
main     = "bin/app.wasm"

[[permissions]]               # 对应 entitlements 和权限说明
path   = "/photos/"
access = "read-write"
reason = "reason.photos"      # 文字在 locales/ 里，两种语言都要有

[[permissions]]
path   = "/contacts/"
access = "read"
reason = "reason.faces"

[[opens]]                     # 对应 CFBundleDocumentTypes
types = ["image/jpeg", "image/png", "image/heic"]
role  = "editor"

[[types]]                     # 对应 UTExportedTypeDeclarations
id   = "photos.album"
from = "application/cbor"

[[routes]]                    # 对应 CFBundleURLTypes，只是这里是 HTTP 路由
prefix = "/photos"

[[watch]]
path = "/photos/"

[[jobs]]
name  = "rebuild-index"
every = "1d"

[[helpers]]                   # 辅助组件有自己的、更小的权限
main        = "bin/thumbnailer.wasm"
permissions = [{ path = "/photos/", access = "read" }]
```

manifest 是人写的，所以用 TOML。内核读取后转成 CBOR 保存。

### 向 macOS 学什么，改什么

| macOS                        | fileOS                                                                                  | 为什么                                    |
| ---------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------- |
| 包含多种 CPU 架构的代码      | **不需要。** WASM 到处都能运行。每个节点把预编译的 `.cwasm` 保存在 `/local/`            | WASM 的长处                               |
| 反向域名的 bundle ID         | **发布者密钥加名字**                                                                    | 不需要域名                                |
| 由 Apple 公证                | **没有中心。** 引擎可以要求用户信任的审核者签名，也可以不要求                           | 规则由用户决定                            |
| Gatekeeper                   | **引擎**                                                                                | 同上                                      |
| Launch Services              | 内核扫描 `/apps/`，在 `/local/` 里建索引，随时可以重建                                  | 派生数据不是状态                          |
| `~/Library/Containers/<id>/` | `appdata/<id>/`（同步）和 `/local/<id>/`（缓存），都随 App 一起删除                     | 比 macOS 更干净                           |
| 用户文件放在 App 外面        | **相同。** 照片在 `/photos/`，不在 App 里                                               | 数据比 App 活得久                         |
| `.appex` 扩展                | **相同，而且更重要。** 缩略图、搜索文字、预览、分享、MCP 工具，都是按文件类型注册的扩展 | 新文件类型只需要一个扩展，所有 App 都能用 |
| 第一次使用时询问（TCC）      | 第一次使用某个路径时询问，答案由引擎记下                                                |                                           |
| 打开面板只给一个文件的权限   | 相同：用某个 App 打开一个文件，就暂时给它这个路径的权限                                 | 选择即授权                                |
| `.dmg` 或 `.zip`             | 直接分享文件夹。需要离线传输时导出成 `.tar`                                             | 运输用的外壳不是 App 本身                 |

最值得学的是**扩展**。Spotlight 和 Quick Look 能支持任何文件类型，是因为每种类型都有一个小扩展。在这里，搜索 App 不需要认识所有格式，只需要调用对应类型的 `SearchExtractor`；文件浏览器不需要认识照片，只需要调用 `Thumbnail` 扩展。每个扩展都有自己的沙箱，权限更小，所以别人可以放心地写。

运行时在**运行的时候**通过 WIT 把主组件、共享组件和扩展连起来，而不是在构建时用 `wac` 合并成一个文件。这样每个部分都可以单独更新和替换。

### App 的生命周期就是文件操作

| 操作           | 实际发生的事                                  |
| -------------- | --------------------------------------------- |
| 安装           | 把 App 文件夹复制或挂载到 `/apps/`            |
| 运行           | 内核发现 `.wasm`，引擎同意，wasmtime 运行它   |
| 更新           | 从发布者那里同步文件夹，或者替换 `.wasm`      |
| 分享给朋友     | 分享这个文件夹                                |
| 所有设备上都有 | `/apps/` 在你的根目录里，会同步到你的所有节点 |
| 卸载           | 删除文件夹，内核同时删除 `/local/<id>/`       |

- 权限跟着 **App 文件夹的 ID** 走，而不是跟着 `.wasm` 的哈希走。更新以后不需要重新授权。如果新的 manifest 要更多权限，由引擎决定是否询问用户。
- 只有和 `id` 对应的发布者密钥能签名这个 App。别人改过的包签名不同，就是另一个 App，能不能运行由引擎决定。

## 网关

网关是给客户端用的一个 HTTP 端口。节点之间的同步不经过它，而是走 libp2p。网关只做两件事：

1. 一个很小的文件系统 API，让客户端按路径读写。
2. **其他请求都按 manifest 里的路由，交给 App 的 `handle-http`。**

网关验证调用者是谁：设备密钥的签名，或者 capability 令牌。然后把调用者交给 App。App 永远不处理密钥。在原型中，网关只监听 `127.0.0.1`，并检查数据目录里的一个令牌。

## 日常功能都是 App

| App        | 使用的路径                            | 提供的功能                            |
| ---------- | ------------------------------------- | ------------------------------------- |
| **photos** | 监听 `/photos/`，写 `/local/photos/`  | EXIF、缩略图、相册                    |
| **search** | 监听所有有权使用的路径，写 `/local/`  | 全文搜索、时间线、地点、关联          |
| **people** | 读聊天、照片和日历                    | 按人、按天、按地点的页面              |
| **chat**   | 每个会话一个流                        | 聊天                                  |
| **vault**  | `/vault/` 下的流                      | Bitwarden API                         |
| **dav**    | `/contacts/`、`/calendar/`、`/files/` | CardDAV、CalDAV、WebDAV               |
| **login**  | 签发 capability（权限很大的 App）     | passkey、OpenID Connect、forward auth |
| **mcp**    | 用户给 AI 的路径                      | MCP                                   |
| **s3**     | 一个文件夹                            | S3 兼容接口                           |
| **push**   | 监听路径                              | Web Push                              |
| **import** | 写入对应的路径                        | Google Takeout、iCloud、聊天记录导入  |
| **backup** | 只用 `store` capability               | 备份到目录、S3 或朋友的节点           |

这些 App 将随 fileOS 一起提供（照片 App 已经实现）。它们和别人的 App 用同样的接口和沙箱。

## 例子

**一张新照片。** 客户端执行 `put /photos/2026/a.jpg`。内核写日志、保存 blob。photos App 收到 `on-change`，生成缩略图写到 `/local/photos/`。search App 收到 `on-change`，更新索引。

**一个家庭群组。** 创建一个文件夹，挂载到 `/groups/family/`，给每个家人 `write`。他们的节点开始同步这个文件夹。chat App 在里面建一个流，这个流就是群聊。

**朋友帮你保存备份。** 给朋友的节点 `store`，带配额。它同步你的文件夹，但只拿到密文。你的节点坏了，用恢复码重建身份，再从朋友那里拿回数据。

**别人使用你的节点。** 你节点的密钥给对方 `use-node`（50 GB）。对方把自己的文件夹放到你的节点上。对你来说，这些文件夹只是密文。

## Crate 结构

```
crates/
  fos            程序本身，只负责把各部分组装起来
  fos-node       把内核组装成一个节点
  fos-gateway    网关
  fos-runtime    App 运行时（wasmtime）：.app 文件夹、引擎、App
  fos-net        libp2p
  fos-store      磁盘：节点密钥、blob、日志、本地键值存储
  fos-sync       同步协议（sans-IO，portable）
  fos-fs         文件夹、日志、顺序、分叉、挂载（sans-IO，portable）
  fos-id         身份：节点证书和身份链接（portable）
  fos-core       格式：CBOR、ed25519、BLAKE3（portable，最底层）
  fos-sim        多节点的确定性模拟，只测内核
apps/            第二个 workspace，编译成 wasm32-unknown-unknown
  fos-app        App 和引擎的 Rust SDK（MIT OR Apache-2.0）
  capability     默认引擎
  photos         照片 App
wit/
  fos.wit        接口（MIT OR Apache-2.0）
```

依赖仍然只能向下。App 和引擎只依赖 `fos-app`。只有 `fos-runtime` 用 wasmtime，只有 `fos-net` 用 libp2p，所以其余代码仍然编译得很快。

## 这个设计带来什么

| 原则         | 这个设计怎么做到                                             |
| ------------ | ------------------------------------------------------------ |
| 只属于你     | 数据是你的文件夹，身份是你的密钥，规则是你的引擎             |
| 以人为中心   | 底层没有数据类型。people 这样的 App 跨所有文件夹按人组织内容 |
| 零运维       | 内核小，很少变化。某个功能出问题，只需要换掉一个 App         |
| 长期可用     | 只有日志和 blob 两种格式。App 没了，数据还在                 |
| 可控         | 每一项权限都是引擎里的一条记录，可以查看，也可以收回         |
| 记忆归你     | AI 的记忆也是一个文件夹，可以查看、修改、删除                |
| 人对人       | 没有作为中心的服务器，只有节点和节点之间的关系               |
| 个人工具     | 一句话生成的小工具就是一个 App，运行在沙箱里                 |
| 开放可替换   | 连访问规则都可以替换，没有任何东西被锁死                     |
| 互助         | 保存、中继、备份，都是"我的节点同意替你保存这些"             |
| 机制而非策略 | 内核只有机制。默认引擎和自带的 App 都是可以替换的默认值      |

它也回答了为什么只有联邦还不够：身份不绑定在域名上，因为身份就是密钥；成本不随网络增长，因为节点只同步自己的文件夹；不需要管理员，因为每个人的引擎就是他自己的规则。

## 原型已经有什么

| 部分                                                  | 是否实现                              |
| ----------------------------------------------------- | ------------------------------------- |
| 文件夹：签名日志、文件、流、挂载、顺序、分叉          | 是（`fos-fs`）                        |
| 同步，以及等待排序节点的写入                          | 是（`fos-sync`，在 `fos-sim` 里测试） |
| 引擎是 WASM 组件，不加限制                            | 是，默认引擎是 `apps/capability`      |
| App 是 WASM 组件，有自己的密钥和资源限制              | 是，照片 App 是 `apps/photos`         |
| `.app` 文件夹像其他文件夹一样同步                     | 是                                    |
| libp2p：TCP、Noise、Yamux、mDNS、中继、DCUtR、AutoNAT | 是，在一台机器上测试了两个节点        |
| `fos` 命令和网关                                      | 是，只供本机客户端使用                |
| QUIC                                                  | 否，见下文                            |
| 用 MLS 加密文件夹                                     | 否                                    |
| App 的 `handle-http`、扩展、辅助组件、网页界面        | 否                                    |
| App 发布者签名；第一次使用时询问用户                  | 否                                    |
| 引擎结果的缓存；`.cwasm` 预编译缓存                   | 否                                    |
| 分块传输 blob                                         | 否：一个 blob 是一条消息，最大 64 MiB |

## 代价和待定问题

1. **编译时间。** 干净构建的大部分时间花在 wasmtime 的编译器（cranelift）上。debug 构建中 cranelift 不做优化，这样它的编译快了约三分之一。在 CI 机器（4 核）上：干净构建 166 秒（预算 360 秒），修改 `fos` 后重建 1.0 秒（预算 5 秒），修改 `fos-core` 后重建 4.2 秒（预算 20 秒）。
2. **QUIC。** `libp2p-quic` 总会打开 quinn 的 `aws-lc-rs` 后端，而 aws-lc-sys 是不允许的（`deny.toml`）。所以原型使用 TCP。中继和打洞在 TCP 上也能工作。等 libp2p 允许使用 `ring`，或者我们修改这条规则时，再加上 QUIC。
3. **每个 crate 只有一个版本。** libp2p 和 wasmtime 会带来一些 crate 的两个版本（比如 `sha2`、`curve25519-dalek` 和 `getrandom`）。每一个都写在 `deny.toml` 里，并注明原因。它们都不来自我们自己的代码。
4. **WASM 的速度。** 缩略图和全文搜索可能比原生代码慢 1.5 到 2 倍，需要在家用硬件上测量。
5. **每次写入都要运行引擎**，同步时每条记录也要运行一次。缓存的效果需要测量。
6. **让人看得懂的分叉。** 不懂技术的人也要能理解"你的副本和主线不同"。
7. **login App** 能签发 capability，权限几乎和内核一样大。用户同意它的方式需要单独设计。
8. **名字。** 如果改名，仓库、文档和域名都要改。改之前应该先确认这个名字没有被别人使用。
