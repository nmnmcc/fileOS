## 一句话

**内核只保存事实：数据、签名、授权和传输。所有功能都是用户自己选择的 WebAssembly 代码，也就是 App。**

## 为什么只有一个基础

一个系统有很多互相独立的概念（组、条目、授权、令牌、副本、中继、插件）时，每个新功能都会再带来一个概念。每个概念都需要自己的代码、自己的测试和自己的同步规则。

fileOS 只有一个基础，一切都建立在它之上。它最初的想法来自 IPFS：内容按哈希命名。但它比 IPFS 小得多，因为它是为个人和家庭的电脑做的，不是为全球网络做的：

- 内容没有全局 DHT。节点通过人找到彼此。
- 默认什么都不公开。
- 节点不会保存任何它没有同意保存的东西。

## 模型

模型有七个概念：**内容、文件、空间、主体、授权、视图和事件**。每一个都在[模型](../access/)一页中，那里也写明了哪些合成一个、哪些分开，以及原因。简单地说：

| 你看到的           | 它是什么                                     |
| ------------------ | -------------------------------------------- |
| 共享相册或网盘     | 一个空间，加上给家人的授权                   |
| 聊天               | 一个目录，每条消息一个小文件                 |
| 一群人             | 一个组：有成员的主体，由一个密钥或一个组拥有 |
| 有多台设备的一个人 | 一个身份（`did:fileos`）和它的节点           |
| 备份或中继         | 对一个空间有 `data.keep` 的节点              |
| 安装 App           | 把 App 放进一个挂载在 `/apps/<name>` 的空间  |
| App 能做什么       | 给 App 密钥的授权，来自它 manifest 中的权限  |
| 收回访问           | 一次收回；由它转授出去的也一起收回           |
| 搬到新服务器       | 让新节点保存你的空间                         |

## 分层

```
┌───────────────────────────────────────────────────┐
│ App（WASM）  photos chat …                        │
├───────────────────────────────────────────────────┤
│ WIT：fileos:app（fs、kv、log、events）+ wasi:http │
├───────────────────────────────────────────────────┤
│ 内核：空间 · 授权 · 同步 · 检查点 ·               │
│       App 运行时 · 网关                           │
├───────────────────────────────────────────────────┤
│ wasmtime · libp2p · 磁盘                          │
└───────────────────────────────────────────────────┘
```

内核对数据没有任何 “应该”。它不知道什么是照片、聊天或密码。在它必须做决定的地方（什么时候做检查点、保留哪些旧版本），它有一个可以替换的策略和一个默认值。

## 内核

### 空间和它们的日志

**空间**是同步、所有者、密钥、检查点和保留策略的单位。它的 ID 是它第一条记录的哈希，所以能自证。

- 每个写入者（一个节点或一个 App，按它的密钥）在一个空间里有自己的**签名日志**。每条记录写明它在哪些记录之后，所以这些日志组成一个**因果图**。没有排序节点：每个节点任何时候都能写，离线时也能；拿到同样记录的节点，不论顺序如何，都得到同样的状态。
- 空间内部是一个**扁平的名字集合**，就像 S3。“目录” 只是一个前缀。名字不会自己移动，所以按前缀的访问权限不会在没人要求时改变。
- **文件**有一个固定的 ID：创建它的那个动作的位置。改名是一个新版本，ID 不变。两台设备同时修改一个文件时，两个版本都并排保留。
- **内容**在内容自己决定的位置切成块，每块按哈希命名。新版本保留没有变的块，同步只发送缺少的部分。

详见[数据](../data/)。

### 授权

访问就是一项**授权**：允许或拒绝，具体的权限（`files.read`、`access.give`、`data.keep` 等），作用在一个名字前缀上，或者按 ID 作用在一个文件上，授予一个密钥或一个组。授权只能以相同或更小的范围转授。收回一项授权时，由它转授出去的也一起收回。拒绝优先。

没有排序节点时，收回和写入可能同时发生。内核采用**强移除**：一个人在访问被收回的同时做的事没有效果。每个节点只凭因果图就得出同样的结论，不需要时钟。

只有当一个节点的密钥对整个空间有 `data.keep` 或 `files.read` 时，它才能保存这个空间，所以空间不会发给没有得到它的节点。

详见[模型](../access/)。

### 检查点

空间的所有者，或者有 `space.checkpoint` 的主体，会签发一个**检查点**：它过去的状态的哈希。之后：

- 节点可以**压缩**：把检查点处的状态保存为基础，丢掉它之前的记录；
- 新节点从签名的**快照**开始，而不是从全部历史开始；
- 旧版本**随时间变稀疏**，按检查点中的保留策略；删除的文件过一段时间后消失；
- 与检查点同时做出的离线修改，由作者的节点**重新写在上面**，并告诉用户。

节点在自己拥有的空间达到 1000 条记录后做一个检查点（这是策略）。

### 节点上的路径

节点有一个**家空间**。其他空间挂载在它里面的某个名字下，所以 `/photos/2026/a.jpg` 就是挂载在 `photos` 的空间中的名字 `2026/a.jpg`。一个挂载就是家空间中 `.mounts/` 下的一个小文件。

```
/photos/...            一个挂载的空间
/apps/Photos.app/...   一个 App 的空间
/identity/...          身份空间：DID 日志和节点证书
```

## 同步和网络：libp2p

我们使用 [libp2p](https://libp2p.io) 做网络，不自己造。

| 我们需要的            | libp2p 提供的                            |
| --------------------- | ---------------------------------------- |
| 节点身份              | PeerId，由节点的 ed25519 密钥生成        |
| 加密传输              | TCP，加上 Noise 和 Yamux                 |
| 没有公网 IP、没有域名 | AutoNAT、DCUtR（打洞）、Circuit Relay v2 |
| 在家庭网络中找到节点  | mDNS                                     |
| 我们自己的同步协议    | request-response                         |

我们不用 IPFS 的那些部分：没有 bitswap，也没有 DHT。节点通过会合节点和你认识的人的节点找到彼此（见[身份与查找节点](../identity/)）。

同步怎样工作：

- 两个节点互相说出每个空间的每条日志有多长，并把对方没有的记录发给对方，只限对方可以保存的空间。
- 新记录发给每个已连接、可以保存这个空间的节点，再由它们继续转发。
- 落后很多的节点会拿到最近一个检查点的快照。
- 内容按哈希向发送记录的节点索取。
- 同步协议是 sans-IO 的。`fileos-net` 把它接到 libp2p 上，`fileos-sim` 把它接到内存中的模拟上。

## App 运行时：wasmtime

我们使用 [wasmtime](https://wasmtime.dev)，不自己造。App 是 `wit/fileos.wit` 中 `app` world 的一个组件：

| 接口                        | 做什么                                               |
| --------------------------- | ---------------------------------------------------- |
| `fileos:app/fs`             | 读、写、追加、列出路径，按授权检查                   |
| `fileos:app/kv`             | 只在本节点的缓存，用于可以重新生成的索引             |
| `fileos:app/log`            | 给人看的消息                                         |
| `wasi:clocks/wall-clock`    | 时间，用于按时间排序的名字                           |
| `fileos:app/events`（导出） | `on-change`：App 监听的路径变了                      |
| `wasi:http`（导出）         | 发给 App 自己的 origin（`<app-id>.localhost`）的请求 |

App 的规则：

- 每个实例都有内存和 fuel 的限制。
- **App 之间只通过文件协作。** 一个 App 写，另一个 App 监听。App 之间没有其他通信方式。
- 我们自己的 App 和别人的 App 用同样的接口和同样的沙箱。

App 的下一步（worker、`wasi:filesystem`、监听选项、选择器）见 [App 作为 Worker](../workers/) 和[模型](../access/)。

## App 包

App 是一个文件夹，和 macOS 一样：`manifest.toml`、`bin/` 中的组件、`ui/` 中的网页界面，以及 `resources/`。需要作为一个文件传递时，`fileos app pack` 生成一个 `.app` 文件：不压缩的 zip，manifest 原样放入，其余文件放在 `payload.tar.zst` 中。

```toml
id       = "photos"
name     = "Photos"
kind     = "app"
version  = "1.4.0"
build    = 142
requires = "fileos:app@0.1.0"
main     = "bin/app.wasm"

[[permissions]]               # App 最多能得到的
path   = "/photos"
access = "read-write"         # 模板：read、read-write、manage
reason = "reason.photos"      # 文字在 resources/locales/ 中

[[watch]]
path = "/photos"
```

安装 App 时，它被放进一个挂载在 `/apps/<name>` 的空间，它的密钥得到 manifest 所申请的授权。它的密钥由节点密钥和 manifest 中的 ID 推导出来，所以更新后不需要重新授权。

## 网关

网关是本机上的一个 HTTP 端口。节点之间的同步不经过它。它在 `fileos.localhost` 提供内核 API，在每个 App 自己的 origin（`<app-id>.localhost`）提供这个 App 的请求。App 拿不到 Cookie，也从不接触密钥。见 [HTTP 与浏览器](../http/)。

## 日常功能都是 App

| App        | 它使用的                                | 它提供的                 |
| ---------- | --------------------------------------- | ------------------------ |
| **photos** | 监听 `/photos`，在缓存中保存索引        | 照片尺寸、相册页面、上传 |
| **chat**   | 每条消息一个文件，在 `/chat/<room>/` 中 | 聊天                     |
| **search** | 监听它能读的内容                        | 全文搜索                 |
| **dav**    | `/contacts`、`/calendar`、`/files`      | CardDAV、CalDAV、WebDAV  |
| **vault**  | `/vault` 下的文件                       | Bitwarden API            |
| **backup** | 只有 `data.keep`                        | 备份到目录或朋友的节点   |

photos 和 chat 已经实现，其他的以后会有。它们和所有人的 App 用同样的接口和沙箱。

## Crate 结构

```
crates/
  fileos            程序本身；只把各部分连起来
  fileos-node       把内核组装成一个节点
  fileos-gateway    网关
  fileos-runtime    App 运行时（wasmtime）：.app 文件和 App
  fileos-net        libp2p
  fileos-store      磁盘：节点密钥、空间的日志和基础、内容
  fileos-space      空间：日志、文件、授权、检查点、同步（sans-IO，可移植）
  fileos-id         身份：did:fileos、节点证书、链接（可移植）
  fileos-core       哈希、密钥、签名、CBOR（可移植）
  fileos-sim        多节点模拟，用于测试
apps/
  fileos-app        App 的 Rust SDK（MIT OR Apache-2.0）
  photos, chat      随 fileOS 提供的 App
wit/fileos.wit      App 接口
```

依赖只向下。App 只依赖 `fileos-app`。

## 代价和未决问题

1. **状态在每次变化后由全部记录重新算出。** 这样简单而正确，但大空间会慢；检查点让空间保持小，以后可以改成逐步计算。
2. **文件名和大小不加密。** 内容是加密的；文件名、大小以及谁写了什么是公开的，因为每个节点都要检查每一条记录。设备还不会更换自己的 HPKE 密钥（见[数据](../data/)）。
3. **只读空间的一部分**（一个前缀或一个文件）还不能发给其他节点：一个节点要么保存整个空间，要么不保存。
4. WASM 和内核在家用硬件上的速度还没有测量。
